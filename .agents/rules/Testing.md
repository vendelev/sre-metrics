# Правила тестирования

## Область и размещение

Применяйте при написании, изменении, запуске и оценке тестов. Сначала прочитайте
проверяемый код, соседние тесты и относящиеся к поведению правила спецификации.
Для `user-auth` сопоставляйте проверки с применимыми BR/AC; идентификаторы можно
указывать в названиях наборов или комментариях без копирования текста контракта.

Файлы `*_test.go` размещайте рядом с кодом. Fixtures — в локальном `testdata/`.
Внешний тестовый пакет `{package}_test` подходит для проверки публичного поведения;
тесты в том же пакете допустимы для необходимых внутренних инвариантов.
Предпочитайте стандартный `testing`, табличные тесты и небольшие тестовые реализации
контрактов. Новые библиотеки тестирования добавляются при обоснованной необходимости.

Проверяйте поведение и значимые эффекты, а не число вызовов каждого внутреннего
метода. Простая структура без логики не требует отдельного теста ради покрытия.
Парсинг и валидация конфигурации, если реализованы, требуют проверок ошибок и границ.
Тесты должны быть минимально достаточными: проверяйте каждое добавляемое правило,
значимые отказы и границы без дублирования одинакового поведения ради покрытия.
Процент покрытия — диагностический показатель; фиксированный порог не менее 75%.

## Уровни проверки

| Уровень | Что проверять |
| --- | --- |
| Domain | Переходы состояния, совместимость фактов, окончательность исхода, длительность |
| Application с memory | Порядок проверок, индексы, лимиты, дедупликация, однократные вклады |
| HTTP-контракт | Полный handler и применимые middleware: разбор запроса, приоритет проверок, статусы, заголовки и тело |
| OTel-контракт | Локальные агрегаты SDK, имена, типы, единицы, атрибуты, Resource и temporality |
| Процесс и pipeline | Остановка, экспорт, преобразование в Collector и фактические серии Prometheus |

Для HTTP-проверок используйте `net/http/httptest`; handler получает запрос как на
реальном входе. Такой тест не доказывает работу контейнерной сети или реальных
отправителей МИС/Auth. Архитектурные импорты проверяются линтером отдельно от поведения.

## Время и конкурентность

Доменное время управляйте через внедрённые часы; реальные ожидания 15 минут
не используются. Проверяйте момент до границы, точное равенство и момент после
для возраста события, deadline и retention в предусмотренной контрактом точности.

Гонки обработчиков и worker воспроизводите барьерами и каналами, а не надеждой
на порядок после `time.Sleep`. Ожидания завершения ограничивайте timeout, чтобы
сбой теста не подвешивал весь набор. При соревновании разных исходов проверяйте
допустимый единственный результат, а не заранее выбранного победителя.

В конкурентных тестах проверяйте не только отсутствие data race, но и инварианты:
один исход, отсутствие двойных вкладов, соблюдение лимитов и согласованность
индексов. Успешный race detector не доказывает правильность алгоритма.
Применяйте `t.Parallel()` только при независимых состоянии, часах и ресурсах.

## Данные, эффекты и внешние границы

Память проверяйте с реальным memory-адаптером, а не только моками CRUD-вызовов.
Для успешных и отклонённых событий проверяйте запись, сохранённые ID и агрегаты.
Учитывайте самостоятельные эффекты срока ожидания и retention: отказ событию
не всегда означает отсутствие любых изменений ранее принятого состояния.

Внешний транспорт подменяйте управляемым экспортёром или тестовым сервером.
Обычный набор тестов не обращается к production, МИС, Auth или случайному Collector.
Тесты живого pipeline должны запускаться явно, иметь описанные зависимости и очистку.

Проверяйте отсутствие ID сценариев, событий и секретов во всех частях метрик.
Fixtures используют синтетические данные; реальные cookies, OAuth-коды, токены
и персональные данные пациентов недопустимы. Отдельно проверяйте безопасную
диагностику, если её требует контракт.

## Запуск и отчёт

Команды определены в [Makefile](../../Makefile): `make test` запускает тесты
с race detector; `make vet` и `make lint` — статические проверки без автоисправлений.
`make fmt` изменяет исходники и не является проверкой без изменений.

В результате указывайте команду, область проверки, успех или причину невозможности
запуска и оставшиеся пробелы. Отсутствие тестовых файлов не означает проверку BR/AC.
Не заявляйте о полном наборе по результату одного теста, о доставке в Prometheus
по локальному агрегату или о сквозной интеграции по тестовому отправителю.
