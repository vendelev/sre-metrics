# Стиль Go-кода

Применяйте при написании, изменении и ревью Go-кода. Ниже изложены правила
оформления этого проекта. Руководства Google использованы как источники,
а не подключены целиком как дополнительные требования:

- [Обзор](https://google.github.io/styleguide/go/).
- [Основные принципы](https://google.github.io/styleguide/go/guide).
- [Конкретные решения](https://google.github.io/styleguide/go/decisions).
- [Практические рекомендации](https://google.github.io/styleguide/go/best-practices).

Ссылки служат для справки и объяснения причин. Отличающиеся рекомендации
Google не заменяют принятые правила проекта.
Для стиля этот документ имеет приоритет над общими рекомендациями загруженных
Go-навыков, в частности по длине строк, nil-срезам и именованию.
Размещение интерфейсов и зависимости определяет [Architecture.md](Architecture.md),
тестирование — [Testing.md](Testing.md), язык текста — [AGENTS.md](../../AGENTS.md).

## Приоритеты

Выбирайте решения в порядке: ясность, простота, лаконичность, удобство
сопровождения, единообразие. Читаемость важнее экономии строк и хитрых приёмов.
Если правило не определяет выбор, придерживайтесь стиля соседнего кода.
Изменяйте стиль в рамках задачи; массовая косметическая переработка требует
отдельного запроса.

## Форматирование и строки

- Исходники оформляйте проектной командой `make fmt` из
  [Makefile](../../Makefile). Её результат имеет приоритет над рекомендациями
  о расположении строк в этом документе и внешних руководствах.
  Актуальные инструменты и параметры берите из Makefile, ограничения импортов —
  из [.golangci.yml](../../module/.golangci.yml).
- Если выражение трудно читать, сначала упрощайте его или выделяйте
  осмысленную переменную. Переносы сигнатур, условий и вызовов, выполненные
  проектным форматтером, сохраняйте.
- Там, где форматтер оставляет выбор, группируйте аргументы по смыслу.
  Число аргументов само по себе не требует отдельной строки для каждого.
- Длинные строковые литералы и URL не разрезайте вручную только ради ширины.
  Комментарии переносите для удобства чтения.
- Выделяя части условий, сохраняйте порядок вычисления и короткое замыкание
  `&&` и `||`: предварительное вычисление всех частей может изменить поведение.

## Именование

- Идентификаторы пишите в `MixedCaps` или `mixedCaps`: `UserCount`, `userCount`,
  `ParseToken`, `maxAttempts`. Константы следуют тому же правилу, не `ALL_CAPS`.
  Первая заглавная буква означает экспорт из пакета; экспортируйте только нужное.
- Сохраняйте регистр аббревиатур: `userID`, `HTTPClient`, `requestURL`, `parseJSON`.
- Имена пакетов — короткие, строчными буквами, без подчёркиваний:
  `config`, `storage`, `userlogin`. Название должно выражать ответственность,
  а не служить общей корзиной `utils`, `common` или `helpers`.
- Подчёркивания допустимы в именах файлов (`user_handler.go`), тестовых функциях
  и суффиксе внешнего тестового пакета (`config_test`). Сгенерированные и
  системные идентификаторы сохраняйте по их контракту.
- Длина имени соответствует области видимости: `i` для короткого цикла,
  `retryInterval` для значения с более широким использованием.
  Предпочитайте понятные сокращения, а не произвольное удаление букв.
- Учитывайте контекст: `users`, а не `userSlice`; `config.Parse`, а не
  `config.ParseConfig`. Имя описывает назначение, а не повторяет тип.
- Обычные методы чтения называйте без `Get`: `Name()`, а не `GetName()`.
  Для вычисления или внешнего запроса уместны `Compute` или `Fetch`.
  Для булевых имён выбирайте естественное понятное условие; обязательного
  префикса `is`/`has`/`can` для каждого поля нет.
- Получатель метода называйте коротко по типу и одинаково во всех его методах:
  `u *User`, `s *Server`, `c *Client`, а не `this` или `self`.
- Конструктор основного типа пакета обычно называется `New`; при нескольких
  создаваемых типах используйте различающие имена вроде `NewRequest`.

## Объявления и структуры

- Для локальной переменной с начальным ненулевым значением предпочитайте `:=`:
  `limit := 100`. Для готового к дальнейшему использованию нулевого значения —
  `var`: `var count int`, `var names []string`.
- Nil-срез допустим: его можно обходить, проверять через `len` и дополнять
  через `append`. Обычно пустой локальный срез объявляйте как `var names []string`.
  Различие JSON `null` и `[]` определяйте контрактом API, а не общим запретом nil.
- Map создавайте перед записью: `counts := make(map[string]int)`.
  Чтение из nil-map допустимо, запись вызывает панику.
- В литералах структур из других пакетов указывайте имена полей.
  Для своих типов также предпочитайте их, если они делают смысл понятнее:

  ```go
  user := User{
      ID:   "example",
      Name: "Пример",
  }
  ```

- Нулевые поля можно опускать, если это не скрывает важное условие.
  Многострочный литерал заканчивайте запятой после последнего элемента
  и закрывающей скобкой на отдельной строке.
- Предварительно выделяйте память при известном размере или подтверждённой
  потребности производительности, а не по произвольному запасу.

## Поток управления и функции

- Ошибки и особые случаи обрабатывайте в начале через `return`, `continue`
  или `break`. Основной успешный путь оставляйте с минимальной вложенностью.
- После ветки, заканчивающейся `return`, убирайте ненужный `else`.
- Если результат нужен дальше, объявляйте его до проверки ошибки:

  ```go
  user, err := loadUser(id)
  if err != nil {
      return err
  }

  return saveUser(user)
  ```

- Функция должна решать связную задачу. Универсального лимита строк или
  аргументов нет; длинный список настроек — повод рассмотреть структуру опций,
  а не автоматически вводить дополнительную абстракцию.
- Предпочитайте явные возвращаемые значения. Возврат без значений допустим
  лишь в небольшой функции, где результат очевиден.
- Если функция принимает `context.Context`, передавайте его первым параметром
  с именем `ctx`; обычно он не должен быть полем структуры или опций.

## Ошибки

- Для обычных отказов возвращайте `error` последним результатом, а не `panic`.
  Успех обозначайте `nil`. Ошибки обрабатывайте или передавайте вызывающему коду;
  обоснованное игнорирование поясняйте комментарием.
- Текст ошибки начинайте со строчной буквы и пишите без завершающей точки,
  сохраняя корректное написание имён и аббревиатур.
- Добавляйте контекст операции, которого ещё нет в исходной ошибке.
  Когда вызывающий код должен иметь доступ к исходной ошибке, оборачивайте
  через `%w`: `fmt.Errorf("загрузка конфигурации: %w", err)`.
  Если раскрытие исходной ошибки не входит в контракт, осознанно преобразуйте
  её или используйте текстовую аннотацию `%v`.
- Категории и типы ошибок проверяйте через `errors.Is` и `errors.As`,
  а не разбором сообщения. Значения ошибок обычно имеют префикс `Err`,
  типы ошибок — суффикс `Error`.
- Обычно ошибку либо возвращают выше, либо окончательно обрабатывают и логируют:
  избегайте повторяющихся записей одной ошибки на каждом уровне.
- Используйте `%q`, когда кавычки помогают увидеть пустую строку или границы
  диагностируемого значения. Секреты и персональные данные не включайте в ошибки.

## Комментарии и организация

- Экспортируемые объявления сопровождайте документирующим комментарием,
  начинающимся с имени: `// Parse проверяет данные и возвращает конфигурацию.`
- Внутренние комментарии объясняют причины, ограничения и неочевидное поведение,
  а не пересказывают очевидные действия кода.
- Связанные типы и функции группируйте по ответственности. Обязательного правила
  «один тип — один файл» нет; имена файлов должны помогать находить код.
- Указатель-получатель используйте для изменения структуры и для типов,
  которые нельзя безопасно копировать, например содержащих `sync.Mutex`.
  Маленькие самостоятельные значения можно передавать по значению.
  Выбор основывайте на корректности, а оптимизацию подтверждайте измерениями.
- Интерфейсы, обобщения и зависимости добавляйте под реальную потребность.
  Размещение интерфейсов, зависимости и управление горутинами определяет
  [Architecture.md](Architecture.md).

## Проверка результата

Проверьте форматирование, имена, обработку ошибок, вложенность и полезность
комментариев во всём изменённом Go-коде. Выполненные команды и ограничения
проверок укажите в отчёте по правилам [AGENTS.md](../../AGENTS.md).
