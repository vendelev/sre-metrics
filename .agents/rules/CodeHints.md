# Подсказки при работе с Go кодом

## Практические рекомендации

### ✅ ДЕЛАЙ

- Перед реализацией изучи соседние файлы того же слоя и связанные тесты: соглашения, импорты,
  зависимости, формат DTO и обработку ошибок. При отсутствии аналога в модуле найди близкую
  по ответственности реализацию в другом модуле. Явные правила проекта имеют приоритет над старым кодом.
- При использовании блокировок строк или исправлении гонок следуй разделу
  [Блокировки строк и CQRS](Architecture.md#блокировки-строк-и-cqrs).
- Создавай интерфейсы когда нужна инверсия зависимостей.
- Выноси логику парсинга и валидации из Controller.
- Всегда используй внедрение зависимостей через конструктор.

### ❌ НЕ ДЕЛАЙ

- При единственной реализации не создавай интерфейс без причины; исключение — Domain-контракт,
  необходимый для инверсии зависимости от Infrastructure или публичного взаимодействия модулей.
- Не создавай DTO для одного входного параметра - это избыточно. Передавай параметр напрямую в `UseCase`.
- Не загружай неиспользуемые зависимости в конструктор.
- Не выполняй запросы к БД для каждого элемента коллекции внутри циклов. Запрет распространяется и на косвенные запросы
  через вызываемые методы и ленивую загрузку связей (N+1).
  Данные загружай заранее пакетным запросом, в цикле работай с подготовленными данными.
  Для записи используй пакетные операции.
  Для больших объёмов допускается обработка порциями с запросами на порцию, а не на каждый элемент.
  Если поэлементные запросы необходимы для корректности, явно обоснуй исключение.
- Query возвращает типизированные структуры или срезы структур, а не нетипизированные наборы полей.
  Query должен маппить данные БД в промежуточные `application/dto`,
  а UseCase — преобразовывать их в `domain/response`.
- Исключение: Query может возвращать DTO из `domain`, если он полностью совпадает с read-model и не требует
  преобразования, обогащения или бизнес-логики. Это уменьшает число промежуточных DTO и проходов по данным.

## Рекомендации по использованию переменных окружения

### Общие принципы

1. **Конфигурация через конфигурационные файлы**: Все параметры приложения должны быть доступны через систему
   конфигурации.
2. **Использование env только в конфигурационных файлах**: Пакет `env` должен использоваться только в
   конфигурационных файлах в каталоге `config/` или в соответствующих файлах модулей.
3. **Избегайте прямого использования env в бизнес-логике**: Никогда не используйте `env` напрямую в:
   - Application,
   - Domain,
   - Infrastructure слоях.

### Правильное использование

1. Создайте конфигурационный файл в каталоге `config` вашего модуля.
2. Для передачи конфигурационных значений используйте контейнер зависимостей.
3. Используйте внедрение зависимостей через параметры конструктора для получения значений.

### Преимущества подхода

1. **Тестируемость**: Конфигурационные значения могут быть легко заменены в тестах.
2. **Гибкость**: Возможность переопределения конфигурации через файлы конфигурации.
3. **Читаемость**: Явное указание зависимостей от конфигурации.

### Переменные окружения в .env файле

Все переменные окружения должны быть определены в файле `.env.example` с примерами значений и комментариями:

```env
# API Configuration
API_KEY=your_api_key_here
```

## Валидация в контроллерах

### Валидация запросов

#### Один параметр

Для запросов с **одним параметром** создание DTO избыточно. Передавай параметр напрямую в `UseCase`.

#### Простые запросы (2-3 параметра)

Для простых запросов используй валидацию напрямую в контроллере.

##### Параметры списка и Request DTO

Даже для 2–3 параметров создавай Request DTO, если они образуют самостоятельный контракт UseCase,
например для списка с пагинацией и фильтрацией:

- есть дефолтные значения;
- есть связанные ограничения;
- значения используются одновременно в валидации, Swagger и UseCase;
- правила должны иметь единую точку определения.

Размещай такой DTO в `domain/request`. Он описывает входные данные UseCase;
это не означает, что все его поля являются инвариантами предметной области.
В пакете Request DTO объявляй типизированные константы дефолтов и ограничений и используй их в валидации и Swagger.
Для простой валидации контроллер может валидировать HTTP-ввод и создавать DTO напрямую.

#### Сложные запросы и Request Factory (4 и более параметров или сложная логика валидации)

Используй **Request Factory**, если создание DTO содержит сложные преобразования, зависимые правила
валидации или переиспользуется несколькими HTTP-входами.

**Преимущества использования Request Factory:**

- ✅ Контроллер остается чистым и компактным
- ✅ Валидация и создание DTO инкапсулированы в одном месте
- ✅ Легко тестировать валидацию независимо от контроллера
- ✅ Переиспользование логики валидации в разных контроллерах
- ✅ Соблюдение принципа единственной ответственности (SRP)
