# Архитектурные правила

## Статус и границы сервисов

Применяйте эти правила при создании пакетов, изменении зависимостей, состояния
или жизненного цикла. Это целевые ограничения реализации; наличие каталога
в каркасе не подтверждает реализацию его ответственности.

Каждый сборщик расположен в `service/{name}/` и владеет своим состоянием,
бизнес-правилами, метриками и настройками. Термин «модуль» здесь обозначает сервис,
а не пакет Go, Go-модуль из `go.mod` или часть единого процесса-монолита.
У него собственные `cmd/main.go`, README и Dockerfile внутри каталога сервиса.
Если сервису понадобятся несколько бинарников, выделяйте для них `cmd/{binary}/`.
Соседние сервисы выпускаются и перезапускаются независимо. Общий `go.mod`
не является общим состоянием или разрешением вызывать код соседнего сборщика.

Вложенный `service/{name}/internal/` скрывает реализацию от соседних сервисов средствами
Go. Импорты между сборщиками запрещены. При добавлении нового сервиса расширяйте
правила изоляции в [конфигурации линтера](../../.golangci.yml).

## Чистая структура и границы слоёв

Основа — [«Чистая структура»](https://vendelev.github.io/Clean-Architecture-Laravel-Demo-Structure/clean-structure/),
адаптированная к Go и независимым сервисам. 
Внутри сервиса выделяются четыре слоя: application, domain, infrastructure и presentation. 
Правила ниже определяют размещение кода; PHP-иерархия классов не переносится в отдельные Go-пакеты автоматически.

| Область                    | Ответственность                                                             | Допустимые зависимости внутри сервиса                                                             |
|----------------------------|-----------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------|
| `internal/domain/`         | Факты, сценарий, исходы, предметные инварианты и контракты внутренних слоёв | Свой domain                                                                                       |
| `internal/application/`    | Операции приложения, порядок проверок, координация состояния и измерений    | Свои application и domain                                                                         |
| `internal/infrastructure/` | Хранение, синхронизация, интеграции с SDK и экспорт                         | Свои infrastructure, application и domain; технические зависимости по необходимости               |
| `internal/presentation/`   | Внешние входы, проверка транспортного формата, ответы и настройки запуска   | Свои presentation, infrastructure, application и domain; технические зависимости по необходимости |
| Корневой пакет сервиса     | Сборка конкретных компонентов и управление жизненным циклом                 | Необходимые пакеты своего сервиса                                                                 |
| `cmd/`                     | Вход процесса, сигналы и код завершения                                     | Публичный пакет запуска своего сервиса                                                            |

Стандартная библиотека допустима по ответственности: HTTP-типы и JSON-транспорт
остаются в presentation, а не проникают в domain/application. Зависимости от SDK
экспорта и реализации хранилища остаются в infrastructure. Матрица задаёт правила проекта; текущий
линтер проверяет только настроенную часть, а не все возможные нарушения архитектуры.

HTTP-вход в presentation проверяет wire-контракт и преобразует результат приложения в HTTP-ответ.
Application работает с разобранными типизированными данными, а не с запросом HTTP.
Предметные правила сосредоточены в domain; application задаёт последовательность
операции и координирует возможности, выходящие за границы одной сущности.

### Куда помещать код

| Что добавляется                                                              | Место в user-login                 |
|------------------------------------------------------------------------------|-----------------------------------|
| Тип события, состояние сценария, правило допустимого исхода                  | `internal/domain/`                |
| Контракт хранения или регистрации измерений, необходимый операции приложения | `internal/domain/`                |
| Операция обработки события или закрытия сценариев по сроку                   | `internal/application/`           |
| Хранение записей в памяти, индексы, лимиты и механизм блокировок             | `internal/infrastructure/memory/` |
| Отображение измерений на инструменты OpenTelemetry и OTLP-экспорт            | `internal/infrastructure/otel/`   |
| Разбор HTTP/JSON, проверка формата запроса, выбор HTTP-ответа                | `internal/presentation/httpapi/`  |
| Чтение и проверка переменных окружения                                       | `internal/presentation/config/`   |
| Создание конкретных компонентов и управление их запуском и остановкой        | `app.go` и технические файлы того же пакета |

### Go-пакеты и категории кода

В user-login domain и application — непосредственно пакеты `domain` и `application`.
Предметные подпакеты выделяйте при появлении самостоятельных областей ответственности.

UseCase, DTO, Entity, ValueObject, Query и Command обозначают роли кода, а не
обязательные каталоги. Связанные типы, операции и их проверки группируйте файлами
одного пакета. Отдельный пакет создавайте для самостоятельной ответственности,
а не для каждого вида типа или файла. HTTP-запросы и ответы принадлежат presentation;
предметные данные не зависят от транспортного формата или структуры таблиц БД.

UseCase — операция приложения; отдельные уровни UseCase/Interactor, шина событий
и разделение Command/Query заранее не требуются. Повторяющиеся части операций
выделяйте по ответственности, без циклических зависимостей пакетов.

## Контракты и сборка

Зависимости передавайте явно через конструкторы. Приложение собирается явной
цепочкой конструкторов в корневом пакете сервиса (решение ревизии 2026-11-04
технического дополнения user-login; ранее использовался Uber Fx). В сборке
связываются реализации с интерфейсами и создаётся приложение перед запуском
обработки событий. Конструкторы возвращают конкретные типы, если нет причины
скрывать реализацию.

Domain, application, infrastructure и presentation не импортируют обвязку сборки
и не получают её через параметры или поля. Компоненты получают только нужные
им зависимости. Глобальный контейнер, Service Locator и поиск зависимостей
из обработчиков (аналог Laravel `app(...)`) не используются.

Ресурсы запускайте после полной сборки: конструкторы не открывают listener
и не запускают фоновые задачи. Используйте явные `Start`/`Stop`; сигналы и код
завершения оставляйте в `cmd`. Порядок запуска задавайте явной
последовательностью, с учётом обратного порядка остановки. Частично неуспешный
запуск должен сам освободить созданные ресурсы. Отмена запуска не должна
отменять контекст остановки; нормализация отмены запуска в успех не выполняется.
На всю остановку и очистку выделяйте один общий бюджет без отдельного резерва
для телеметрии; контекст запуска не используйте для фоновой задачи.
Ошибки сборки возвращайте вызывающему коду; сохраняйте проверки
сборки и освобождения ресурсов при ошибке запуска.

Фактический порядок запуска и остановки описан
в [README user-login](../../service/user-login/README.md#владение-ресурсами-и-остановка).

Интерфейс определяется конкретной потребностью вызывающего кода. Контракты,
через которые application обращается к infrastructure, размещайте в domain;
infrastructure реализует их, а app.go передаёт реализации в application.
Это принятое в проекте правило из «Чистой структуры», а не требование языка Go.
Контракты не раскрывают HTTP-типы, SDK телеметрии и детали хранения.
Интерфейсы создавайте по необходимости, а не для каждого конкретного типа.

В общий пакет выносите только подтверждённо повторяющийся технический механизм.
Общий код не импортирует сервисы и не объединяет их бизнес-правила. Пустой
`platform/` или универсальный движок сценариев заранее не создаются.

## Состояние, время и измерения user-login

Последовательность проверок и их эффекты определяются спецификацией, а не
удобством CRUD-интерфейса. Хранение обязано обеспечивать согласованность доступа
к сценариям, глобальному индексу событий и лимитам относительно HTTP и worker.

Динамическое время берите внутри атомарной операции. Механизм синхронизации
оставляйте адаптеру хранения; предметный смысл переходов и порядок обработки —
внутренним слоям. Текущее устройство хранения описано в
[README user-login](../../service/user-login/README.md#устройство-и-запуск).

Согласованность изменения сценария и однократной регистрации измерений в локальном агрегате
проектируйте явно. Отдельно различайте регистрацию измерения и сетевой экспорт:
OTLP-вызовы не выполняются под блокировкой сценариев и не являются условием HTTP 204.
Расчёт часового окна и SLO остаётся в мониторинге.

HTTP и фоновые задачи должны использовать одно состояние своего сборщика,
без отдельных экземпляров хранилища для каждого входа.
Запуск и остановку goroutine контролирует приложение; для каждой есть способ
завершения. Порядок штатной остановки должен обеспечить завершение обработки
и прекращение изменений состояния до финального экспорта с ограниченным ожиданием.
Согласованные настройки user-login описаны в
[README сервиса](../../service/user-login/README.md#настройки); изменение их политики
требует отдельного согласования. Если экспорт ещё не подключён, завершайте остановку
после прекращения изменений состояния, без фиктивного экспортёра.
