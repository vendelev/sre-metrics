# Архитектурные правила

## Статус и границы сервисов

Применяйте эти правила при создании пакетов, изменении зависимостей, состояния
или жизненного цикла. Это целевые ограничения реализации; наличие каталога
в каркасе не подтверждает реализацию его ответственности.

Каждый сборщик расположен в `module/{name}/` и владеет своим состоянием,
бизнес-правилами, метриками и настройками. Термин «модуль» здесь обозначает сервис,
а не пакет Go, Go-модуль из `go.mod` или часть единого процесса-монолита.
У него собственные `cmd/{binary}/main.go`, README и Dockerfile внутри каталога модуля.
Соседние сервисы выпускаются и перезапускаются независимо. Общий `go.mod`
не является общим состоянием или разрешением вызывать код соседнего сборщика.

Вложенный `module/{name}/internal/` скрывает реализацию от соседних сервисов средствами
Go. Импорты между сборщиками запрещены. При добавлении нового сервиса расширяйте
правила изоляции в [конфигурации линтера](../../.golangci.yml).

## Clean Architecture

| Область | Ответственность | Допустимые зависимости внутри сервиса |
| --- | --- | --- |
| `internal/domain/` | Факты, сценарий, исходы и предметные инварианты | Свой domain |
| `internal/application/` | Операции приложения, порядок проверок, координация состояния и измерений | Свои application и domain |
| `internal/adapters/` | HTTP, память, OTel и другие конкретные механизмы | Свои application и domain; технические зависимости по необходимости |
| `internal/config/` | Чтение и проверка настроек запуска | Технические средства конфигурации, без запуска приложения |
| `app.go` | Сборка конкретных компонентов и управление жизненным циклом | Необходимые пакеты своего сервиса |
| `cmd/{binary}/` | Вход процесса, сигналы и код завершения | Публичный пакет запуска своего сервиса |

Стандартная библиотека допустима по ответственности: HTTP-типы и JSON-транспорт
остаются в адаптерах, а не проникают в domain/application. Зависимости от SDK
экспорта и хранилища остаются снаружи. Матрица задаёт правила проекта; текущий
линтер проверяет только настроенную часть, а не все возможные нарушения архитектуры.

HTTP-адаптер проверяет wire-контракт и преобразует результат приложения в HTTP-ответ.
Application работает с разобранными типизированными данными, а не с запросом HTTP.
Предметные правила сосредоточены в domain; application задаёт последовательность
операции и координирует возможности, выходящие за границы одной сущности.

## Контракты и сборка

Зависимости передавайте явно через конструкторы. Конкретные адаптеры связывайте
в `app.go`; контейнер DI и поиск зависимостей из обработчиков не используются.
Конструкторы возвращают конкретные типы, если нет причины скрывать реализацию.

Интерфейс определяется потребностью вызывающего кода и обычно располагается
рядом с внутренним потребителем. Например, порты хранения и регистрации измерений
могут принадлежать application. Интерфейс для каждого типа, обязательный слой
`services`, CQRS и универсальная шина событий не требуются.

В общий пакет выносите только подтверждённо повторяющийся технический механизм.
Общий код не импортирует сервисы и не объединяет их бизнес-правила. Пустой
`platform/` или универсальный движок сценариев заранее не создаются.

## Состояние, время и измерения user-auth

Последовательность проверок и их эффекты определяются спецификацией, а не
удобством CRUD-интерфейса. Хранение обязано обеспечивать согласованность доступа
к сценариям, глобальному индексу событий и лимитам относительно HTTP и worker.

Динамическое время берите внутри атомарной операции. Механизм синхронизации
реализует memory-адаптер; предметный смысл переходов и порядок обработки остаются
во внутренних слоях. Конкретный контракт атомарной операции и механизм блокировок
ещё требуют проектирования — каркас их не задаёт.

Согласованность изменения сценария и однократного вклада в локальный агрегат
проектируйте явно. Отдельно различайте регистрацию измерения и сетевой экспорт:
OTLP-вызовы не выполняются под блокировкой сценариев и не являются условием HTTP 204.
Расчёт часового окна и SLO остаётся в мониторинге.

Фоновые задачи работают с тем же состоянием внутри процесса своего сборщика.
Запуск и остановку goroutine контролирует приложение; для каждой есть способ
завершения. Порядок штатной остановки должен обеспечить завершение обработки
и прекращение изменений состояния до финального экспорта с ограниченным ожиданием.
Численные timeout и эксплуатационные настройки согласуются отдельно.
