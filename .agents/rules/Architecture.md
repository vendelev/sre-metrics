# Архитектура проекта

## Основные принципы и паттерны архитектуры

1. **CQRS (Command Query Responsibility Segregation)**
2. **Clean Architecture**
   - Многослойная архитектура с четкими зависимостями
   - Доменно-ориентированное проектирование
   - Бизнес-логика, независимая от фреймворка
3. **Modular Monolith**
   - Независимые модули
   - Модульные API и контракты
   - Четкие границы модулей

## Ключевые соглашения

- **Функциональный модуль**: Максимально самодостаточная часть продукта, отвечающая за определённый функционал.
  Каждый модуль может содержать публичные доменные интерфейсы, сущности или события, определяющие границы его
  использования (API модуля).

- **UseCase**: Реализация конкретного варианта поведения пользователя (описывает, что пользователь хочет сделать).

- **Orchestrator**: Координация нескольких самостоятельных UseCase в рамках одного составного сценария.

- **DTO** (Data Transfer Object): Типизированная структура данных для передачи между слоями и модулями.

- **События** (Event): Специализированный DTO для взаимодействия компонентов внутри модуля и между модулями. Три типа:
  - **Уведомления** (Notification): DTO описывающий сообщение о завершённом действии в прошлом.
    Может быть синхронным или асинхронным.
    Много получателей возможно.
    Пример: *пациент был зарегистрирован*.
  - **Запросы** (EventQuery): DTO описывающий синхронный запрос на получение данных.
    Ровно один получатель (один ответ).
    Пример: *получить историю пациента*.
  - **Команды** (EventCommand): DTO описывающий синхронное указание другому модулю выполнить действие:
    - создать,
    - изменить,
    - удалить данные.

    Ровно один получатель (одна обработка).
    Пример: *создать запись в журнале*.

## Структура директорий в модуле

### Api

Публичное API модуля. 
Только межмодульные интерфейсы, события и dto.
Экспортируемые типы и интерфейсы пакета доступны внешним потребителям.

### Bootstrap

Принимает готовые типизированные настройки.
Отвечает за создание компонентов, DI, routing, сборка обработчиков и внутренних подписок на события:

- Может импортировать любые внутренние пакеты своего модуля.
- Предоставляет собранные HTTP-обработчики, обработчики очереди, консольные команды и публичные сервисы.
- Создание компонентов отделено от запуска фоновой работы.
- Внутренние слои не импортируют bootstrap.
- "Bootstrap приложения" управляет общим жизненным циклом, используя предоставленные модулем методы запуска и остановки.

**Пример структуры:**

```text
patient/
│   ├── bootstrap
│   │   ├── app.go
│   │   ├── runtime.go
│   │   ├── di.go
│   │   └── route.go
```

### Config

Читает окружение и определяет типизированные настройки модуля и его компонентов: таймауты, лимиты, настройки поведения.

Внутренние компоненты могут импортировать свой {Module}/config.
А {Module}/config не должен импортировать bootstrap и реализации из internal.

**Пример структуры:**

```text
patient/
│   ├── config/
│   │   ├── http.go
│   │   └── memory.go
```

### Application

Содержит реализацию бизнес-логики модуля:

- **usecase**: Пакет, реализующий вариант использования. Координирует работу Command, Query, Service.
- **orchestrator**: Координирует несколько UseCase, не реализуя логику отдельных операций.
- **command**: Пакет "команд" CQRS, реализующие логику изменения данных (создание, обновление, удаление).
  Для упрощения реализации команда может напрямую работать с БД модуля и его эксплуатационными хранилищами,
  включая PostgreSQL, ClickHouse и другие СУБД.
  Запись аудита, технического или эксплуатационного журнала является командой.
- **query**: Пакет "запросов" CQRS, реализующие логику получения данных.
  Для упрощения реализации логики разрешается работать с БД напрямую.
- **service**: Самодостаточная реализация специфичной логики (не зависит от фреймворка).
  Пример: калькулятор, парсер, валидатор.
- **dto**: Объекты для передачи данных внутри Application слоя.
  Например, UseCase получает RequestDTO, создает и обогащает локальную DTO, передает DTO в Command.
- **factory**: Фабричные методы для создания DTO, Response, ValueObject.

Application содержит SQL в Command/Query.
Application подготавливает типизированные данные и при необходимости публикует события из `domain`.
Форматирование результата для пользователя, шаблоны и генераторы специального контента относятся к Presentation;
Связь с Responder описана в разделе [«Формирование представления результата»](#формирование-представления-результата).

#### Оркестрация нескольких UseCase

Если в рамках одного сценария требуется согласованно выполнить несколько самостоятельных UseCase,
допускается создать оркестратор в `application`.
Это возможность, а не обязательный дополнительный слой для каждого сценария.

Оркестратор должен заниматься только оркестрацией:

- Определять порядок вызовов UseCase и передавать результаты между ними.
- Выбирать следующий шаг по результату предыдущего, в том числе завершать сценарий досрочно.
- Управлять предусмотренными сценарием ветками обработки ошибок, вызывая соответствующие UseCase.
- Возвращать итог сценария вызывающему коду.

Бизнес-проверки, вычисления, загрузку и сохранение данных, подготовку данных событий,
публикацию событий и внешние интеграции делегируй UseCase. Оркестратор не обращается напрямую
к Command, Query, хранилищам или адаптерам интеграций. Простая передача DTO и их полей между шагами
не считается самостоятельной обработкой данных.

Не создавай оркестратор для одного делегирующего вызова и не дроби цельный UseCase только ради его появления.
Совместное участие в одном сценарии не является причиной объединять независимые UseCase в один пакет.

Последовательный вызов UseCase сам по себе не обеспечивает атомарность:

- По умолчанию каждый UseCase управляет транзакцией своей операции.
- Если нескольким шагам нужна общая транзакция, её границы задаёт оркестратор через принятую в проекте
  абстракцию управления транзакциями; это часть координации, а не доступ к данным.
  Все участвующие операции используют одно соединение и не фиксируют части сценария независимо.
- Механизм участия UseCase в общей транзакции определяется соглашениями рабочего проекта.
  Перед реализацией изучи существующее управление транзакциями и зафиксируй выбранный подход
  в документации проекта. UseCase не обязан самостоятельно определять наличие внешней транзакции;
  важно обеспечить единые границы фиксации и отката.
- Не включай внешние отправки в такую транзакцию: выполняй их после успешного commit через предусмотренный
  сценарием UseCase или Listener события. Если требуется надёжная доставка, делегируй UseCase запись события
  в outbox в той же транзакции; обработка outbox инициирует отправку после commit.
- Если шаги фиксируются независимо, явно определи поведение при частичном выполнении сценария;
  ошибка следующего шага не отменяет уже завершённые операции автоматически.

#### Блокировки строк и CQRS

- **Захват блокировки — команда**: SQL `SELECT ... FOR UPDATE` изменяет состояние блокировок БД,
  поэтому размещай его в `application/command`, даже если запрос начинается с `SELECT`.
- Для блокировки строки используй метод `SetLockForUpdate(<тип идентификатора>): error`
  соответствующего Command. `nil` означает, что подходящая запись найдена и заблокирована;
  `error` — подходящая запись не найдена. Команда может возвращать результат своего выполнения:
  это не превращает её в Query. Обычное чтение данных остаётся в Query, захват блокировки — в Command.
- При soft delete включай в запрос блокировки условие неудалённой записи согласно схеме таблицы:
  `deleted = false` для булевого флага или `deleted_at IS NULL` для временной метки удаления.
  При занятой блокировке запрос ожидает её освобождения; ошибки БД возвращаются как error.
- UseCase задаёт границы транзакции своей операции, если не участвует в общей транзакции
  [оркестратора](#оркестрация-нескольких-usecase), и явно выполняет операции в порядке:
  **CreatePatient.SetLockForUpdate → проверка результата → дополнительные бизнес-проверки → Command-изменение**.
  Все операции должны использовать одну транзакцию; блокировка удерживается до commit или rollback.
- Для защиты от гонки все конкурирующие сценарии должны блокировать одну и ту же строку перед проверками
  и записью. Например, удаление профиля, создание раздела и перенос раздела в профиль блокируют строку
  этого профиля. Одна транзакция только вокруг удаления не защищает от параллельного создания раздела.

**Пример структуры:**

```text
patient/internal/
├── application/
│   ├── usecase/
│   │   ├── create_patient.go
│   │   └── notify_patient.go
│   ├── orchestrator/
│   │   └── register_patient.go
│   ├── command/
│   │   └── create_patient.go
│   ├── query/
│   │   └── get_patients_by_age.go
│   ├── service/
│   │   └── patient_age_mapper.go
│   ├── dto/
│   │   └── create_patient.go
│   └── factory/
│       └── create_request_patient.go
```

### Domain

Предметная область модуля:

- **contract**: Контракты (интерфейсы) для инверсии зависимостей внутри модуля.
- **request**: DTO входящих данных в Controller/Console. Immutable.
- **response**: DTO исходящих данных из Controller. Immutable.
- **dto**: Структуры для передачи слоями. Immutable.
- **error**: Общие ошибки модуля
- **entity**: Описание структуры таблицы БД.
- **valueobject**: Узкоспециализированный DTO, иногда, со встроенной валидацией. Immutable.
- **validation**: Методы для проверки бизнес-требований к данным.
- **event**: Уведомления, Запросы, Команды для взаимодействия внутри модуля. Immutable.
  В том числе события Application, на которые реагируют Listener в Presentation.

Документация модуля располагается в его `{Module}/README.md`, дополнительные локальные материалы — в `{Module}/docs/`.
Сквозные сценарии интеграций размещаются в `docs/integration/`.

**Пример структуры:**

```text
patient/internal/
├── domain/
│   ├── contract/
│   │   └── external_medical_system.go
│   ├── dto/
│   │   └── notification.go
│   ├── request/
│   │   └── create_patient.go
│   ├── response/
│   │   └── patient.go
│   ├── entity/
│   │   └── patient.go
│   ├── valueobject/
│   │   ├── patient_id.go
│   │   └── email.go
│   ├── validation/
│   │   └── patient_age.go
│   ├── event/
│   │   └── patient_created.go
```

### Infrastructure

Реализация интеграций с внешними сервисами и другими модулями (Anti-corruption layer):

- **adapter**: Реализует Domain интерфейсы для работы с внешними сервисами или 
  api-интерфейсы для работы с другими модулями.
- **{LibName}**: Адаптеры для взаимодействия с внешними библиотеками.

**Пример структуры:**

```text
patient/internal/
├── infrastructure/
│   └── http/
│       └── server.go
```

### Presentation

Точка входа и выхода из модуля:

- **http/controller**: HTTP контроллеры для обработки REST запросов.
- **http/middleware**: Middleware компоненты.
- **console**: Крон-скрипты, демоны, консольные команды.
- **listener**: Обрабатывает события и данные, которые ему передаёт механизм синхронной и асинхронной доставки:

  - шина,
  - очередь,
  - файловый приёмник.

- **responder**: Общий пакет слоя Presentation для формирования специального контента из готовых данных:
  email, Excel, PDF, сообщений в Telegram. Шаблоны располагаются в подкаталоге `template` соответствующего Responder.

**Пример структуры:**

```text
patient/internal/
├── presentation/
│   ├── http/
│   │   ├── controller/
│   │   │   └── patient.go
│   │   └── middleware/
│   │       └── auth.go
│   ├── console/
│   │   ├── sync_patients.go
│   ├── listener/
│   │   └── patient_created.go
│   ├── responder/
│   │   ├── email/
│   │   │   ├── patient_welcome_email.go
│   │   │   └── template/
│   │   │       └── welcome.html
│   │   └── report/
│   │       ├── create_tax_excel_report.go
│   │       └── template/
│   │           └── tax-report.xlsx
```

#### Формирование представления результата

Application не вызывает Responder напрямую и не получает его через интерфейс для обхода границ слоёв.
Для реакции на результат бизнес-сценария используй событие из `domain/event`:

```text
Application/UseCase
  → Domain/Event/PatientCreatedNotification
    → Presentation/Listener/PatientCreatedListener
      → Presentation/Responder/Email/PatientWelcomeEmail
        → Template/welcome.html
      → отправитель готового письма
```

Стрелки показывают поток выполнения, а не зависимости между структурами.
UseCase зависит от типа события и принятого в проекте контракта публикации событий, а не от Listener или Responder.
Подписки и DI настраиваются в:

- `{Module}/bootstrap` - Внутренние зависимости и подписки модуля
- `cmd/{AppName}/bootstrap` - Связи между модулями и подключение их к приложению

**Ответственность компонентов:**

- **UseCase** выполняет бизнес-сценарий и публикует событие с типизированными данными результата.
- **Listener** получает событие, вызывает Responder и организует отправку готового контента.
  Отправку делегирует принятому в проекте отправителю или инфраструктурному адаптеру своего модуля.
  Бизнес-операции и запись результатов доставки выполняются через соответствующие UseCase, а не внутри Responder.
- **Responder** преобразует готовые данные в представление. Например, группировка, сортировка,
  форматирование дат, заголовков и подписей для отображения. Он не выполняет бизнес-проверки,
  не обращается к БД, не публикует события и не отправляет сообщения.
- **Отправитель** принимает готовый контент и параметры доставки. Он не зависит от Responder в Presentation.

**Размещение:**

- Для непосредственного формирования результата консольной команды вызывай `presentation/responder`
  из `presentation/console` с данными, возвращёнными Application. Не вводи событие только ради обычного вывода.

### Валидация и доверие между слоями

- Для каждого инварианта определяйте владельца. Транспорт проверяет:
  - внешний формат, 
  - domain — предметную допустимость, 
  - инфраструктура — собственные технические ограничения.
- Перед добавлением защитной проверки проследите все рабочие пути получения значения: 
  где оно создаётся, проверяется и может изменяться.
- Внутри доверенной цепочки используйте гарантии предыдущих компонентов.
  Повторная проверка оправдана при независимой границе доверия либо конкретном
  достижимом пути нарушения; укажите этот путь в обосновании изменения.
- Если сущность может сформировать некорректное значение через свой обычный API, укрепляйте инвариант в сущности, 
  а не компенсируйте дефект в потребителях.
- Выбирайте минимальное решение для текущих требований и существующих вызовов.
  Гипотетические будущие вызовы сами по себе не обосновывают дополнительную валидацию, абстракцию или обработку ошибок.

## Инициализация приложения

- **cmd** - Файлы инициализации приложения
  - **{AppName}** - Отдельное исполняемое приложение: HTTP-сервер, обработчик очереди или консольная команда.
    Одно приложение может одновременно запускать HTTP-сервер, обработчики очередей и фоновые задачи.
    - **bootstrap** - Сборка приложения и управление его жизненным циклом: запуск, остановка и освобождение ресурсов:
      - сборка компонентов отделена от запуска фоновой работы;
      - владелец ресурса отвечает за его освобождение;
      - неуспешный запуск освобождает уже созданные ресурсы;
      - каждая goroutine имеет владельца и способ завершения;
      - контекст остановки не наследует отмену запуска;
      - порядок остановки учитывает зависимости и завершение обработки;
      - остановка ограничена явно определённым бюджетом.
    - **config** - Общие настройки приложения, параметры окружения
    - **main.go** - Точка входа процесса: обработка сигналов, вызов запуска приложения и определение кода завершения

**Пример структуры:**

```text
cmd/patient-webserver
│   ├── bootstrap
│   │   ├── app.go
│   │   └── runtime.go
│   ├── config/
│   │   ├── env.go
│   └── main.go
```

Это "максимальная" сложность одного модуля. Не требуется создавать все папки сразу.

## Структура директорий в проекте

- **docs** - Общая документация разработки, технические пояснения и описание интеграций.
- **docker** - Файлы для сборки Docker контейнеров.
- **backend** - Реализация модульного монолита с REST API или Консольных команд
  - **pkg** - Переиспользуемые компоненты
  - **cmd** - Точки входа и сборка исполняемых приложений
    - **{AppName}** - Исполняемое приложения  
      - **bootstrap** - Соединение модулей и управление жизненным циклом приложения
      - **config** - Общая конфигурация приложения (environment)
  - **{ModuleName}** - Функциональный модуль.
    - **api** Публичное API модуля. Только межмодульные интерфейсы, события и dto
    - **bootstrap** - Сборка компонентов модуля (DI, routing)
    - **config** - Конфигурация модуля и его компонентов (environment)
    - **internal** - Скрывает реализацию от соседних модулей средствами Go
      - **application** - Содержит реализацию бизнес-логики модуля
      - **domain** - Предметная область модуля
      - **infrastructure** - Реализация интеграций с внешними сервисами и другими модулями (Anti-corruption layer)
      - **presentation** - Точка входа и выхода из модуля
  - **temp** - Временные файлы, логи и отчёты инструментов.
  - **go.mod** - Go-модуль всего приложения

## Правила зависимостей между слоями

**Разрешённые зависимости определяются следующей матрицей:**

| Слой               | Может использовать                                                                                        |
|--------------------|-----------------------------------------------------------------------------------------------------------|
| **Presentation**   | Cвой модуль: Infrastructure, Application, Domain, Config; Api (свой и чужой модуль), внешние библиотеки |
| **Infrastructure** | Cвой модуль: Application, Domain, Config; Api (свой и чужой модуль), внешние библиотеки |
| **Application**    | Cвой модуль: Application, Domain, Config; Api (свой и чужой модуль), внешние библиотеки|
| **Domain**         | Cвой модуль: Domain, Config; Api (свой и чужой модуль)|
| **Api**         | Api (свой и чужой модуль)|
| **Bootstrap модуля** | Config, Api, внутренние пакеты, публичные контракты необходимых зависимостей|
| **Bootstrap приложения** | Bootstrap, Config и Api подключаемых модулей|
| **Config модуля** | Config (свой модуль)|

Эта матрица регулирует зависимости между внутренними слоями, а для технических библиотек существуют отдельные правила.

**Внедрение зависимостей (DI):**

- Не требуется создавать интерфейс, если существует одна реализация.
  Не создавай интерфейс «на будущее»: второй вариант должен уже существовать или быть подтверждён требованием.
  НО для использования Infrastructure-реализации в Application слое обязательно создайте интерфейс в Domain.
- Пример: Application использует интерфейс `ExternalMedicalSystem` (определённый в Domain),
  который реализует в адаптере `ExternalMedicalSystem` в Infrastructure для работы с внешним сервисом.

## Зависимости между модулями

Модуль должен быть максимально независим от других модулей.
Модули могут взаимодействовать между собой двумя способами:

1. **Синхронно через интерфейсы**: "Модуль A" использует Api интерфейсы "модуля B" через Anti-corruption layer (
   Adapter в Infrastructure).
2. **Синхронно/Асинхронно через события**: "Модуль A" генерирует Api Event, подписчики (Listener) других
   модулей его обрабатывают.
   Внутренние события модуля определяются в internal/domain/event. 
   Межмодульные события и необходимые для них типы публикуются в api.

## Когда создавать интерфейсы

Интерфейс (контракт) обязателен в следующих случаях:

1. **В рамках модуля**: Существует 2+ реализации функциональности.
   - Пример: `SoapMedicalSystem` и `HttpMedicalSystemA` реализуют интерфейс `MedicalSystem` для работы
     с внешней системой.
2. **Для инверсии зависимостей**: Application слой зависит от Domain интерфейса, который реализует Infrastructure.
   Интерфейс создаётся для внешнего сервиса или другого модуля; он не требуется команде,
   напрямую записывающей данные в БД при единственной реализации.
3. **Для взаимодействия модулей**: При использовании функциональности из другого модуля всегда через его Api интерфейс.

Интерфейс сам по себе не делает код расширяемым. Вне обязательных архитектурных границ
перед его созданием проверь, есть ли реальная ось изменений: несколько вариантов поведения,
которые будут развиваться независимо. Для единственного текущего сценария используй конкретный пакет
и выделяй контракт, когда появится второй вариант или подтверждённое требование к нему.
Не создавай интерфейс только ради mock-объекта или теста.

## Валидация и типизация

### На уровне Controller (Presentation)

Валидируются **структурные** характеристики данных:

- Обязательность полей (required / nullable).
- Типы полей (string, int, array, и т.д.).
- Базовые форматы (email, date, и т.д.).
- Цель: Гарантировать, что можно создать типизированный DTO из входящего запроса.

**Инструменты:** В контроллере или `Application/Factory` для сложного запроса.

### На уровне UseCase (Application)

Валидируются **бизнес-требования** к данным:

- Логические ограничения (пациент старше 18 лет?).
- Состояния (можно ли выполнить действие в текущем статусе?).
- Доступность (есть ли доступ к ресурсу?).
- Цель: Гарантировать корректность бизнес-процесса.

**Инструменты:** Validation в Domain, проверки в UseCase или Service.

### Для сложных входных данных

Выносите логику парсинга и валидации из Controller в Factory или valueObject.

## Гранулярность ответственности в структуре

### Оставлять методы в одной структуре, если

- Зависимость из конструктора используется в **нескольких методах** для похожей функциональности.
- Методы отвечают за одну зону ответственности.
- Методы изменяются по запросам одного актора и по одной бизнес-причине.

### Разделять на разные структуры, если

- Части структуры меняются независимо по запросам разных акторов или по разным бизнес-причинам.
- В одном структуре накапливаются несколько подтверждённых вариантов поведения, и новый вариант регулярно меняет
  существующий код.
- Пример: Создание отдельного service `notification` вместо загрузки в основной UseCase.
- **Преимущество**: Избегаете загрузки неиспользуемых зависимостей, улучшаете тестируемость.

Не дели пакет или структуру только ради количества структур, методов или интерфейсов. 
До появления независимой причины изменения предпочитай простую реализацию и рефакторинг по фактическому требованию.
