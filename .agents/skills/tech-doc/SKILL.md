# Создание технической документации

## Роль

Описывай фактическое устройство системы для разработчиков и сопровождающих: ответственность модулей,
бизнес-правила, сценарии, контракты и существенные явные и неявные связи.

## Входные данные

Определи область по запросу и согласованному контексту: конкретные модули, сценарий, интеграция или проект целиком.
Если область не определена, уточни её до записи документов. Документируй реализованную систему;
не превращай исследование в разработку функциональности или перенос файлов без запроса.

В этом репозитории модуль — сервис в `service/{name}/` со своей точкой входа,
бинарником и контейнером. Это не пакет Go и не отдельный Go-модуль: `go.mod` общий.
Описывай проект как «репозиторий независимых сервисов с модульной организацией кода».
Различай сборщики, внешних отправителей событий, Collector, хранилище метрик и общие пакеты.
Кластеры Graphify — группы для навигации, а не автоматически установленные границы модулей.

Глубина изучения кода не определяет объём документа: в результат включай только сведения,
необходимые для понимания модуля, пакета или всего проекта.

## Процесс

### 1. Собери факты

Изучи:

- [`AGENTS.md`](../../../AGENTS.md);
- корневой README, README затронутых модулей и относящиеся к области документы в `docs/`;
- исходный код, конфигурацию и тесты затронутой части проекта.

Исторические handoff-документы исключай из источников фактов и текущих требований, даже если на них ссылается
README или граф. Сами файлы сохраняй. Существующее описание сверяй с кодом и конфигурацией;
тест подтверждает наличие проверяемого сценария, а успешный запуск — его прохождение в указанном окружении.

Если используешь Graphify, прочитай [правила графа и хранения в Git](references/graphify.md).
Граф служит указателем на доказательства, а не источником истины.

Для существенных утверждений сохраняй ссылки на исходники, конфигурацию или тесты.
Отдельно отмечай подтверждённое поведение, гипотезы и границы проверки. Например:
«проверена отправляющая сторона; получатель и конфигурация брокера не проверены».
Проверяй существенные скрытые зависимости через ручную сборку, импорты, конфигурацию
и общее состояние. Локальная регистрация метрики, OTLP-экспорт и сбор Prometheus —
разные уровни подтверждения. Cumulative temporality сама по себе не гарантирует доставку.
Если есть только каркас, описывай его текущие точки входа и ограничения;
назначение будущего сервиса обозначай как цель, а не реализованное поведение.

Заверши сбор, когда каждое существенное утверждение имеет доказательство либо явно обозначено как
непроверенное. Вопрос пользователю нужен, если неизвестное мешает корректному описанию;
иначе зафиксируй ограничение, не блокируя всю документацию.

### 2. Выбери размещение

| Материал | Место |
| --- | --- |
| Краткое назначение проекта и каталог модулей | Корневой `README.md` |
| Краткое описание и статус каждого модуля | `service/{name}/README.md` |
| Пояснения конкретного модуля | `service/{name}/docs/` при необходимости |
| Общие инструкции разработки и технические пояснения | `docs/` |
| Правила для агентов | `.agents/rules/` |
| Навигация по графу, статус и политика хранения | `graphify-out/README.md` |
| Автоматические результаты Graphify | `graphify-out/graph.json`, `GRAPH_REPORT.md` и другие результаты инструмента |

У каждого описания одно основное место. Создавай дополнительные пояснения, только
когда они отвечают на отдельный нужный вопрос. Существующие документы и код
переноси только по запросу. Не создавай пустые модули ради будущих ссылок.

### 3. Напиши документ

Строй описание вокруг ответственности и сценариев, а не перечня классов.
Во всех документах используй условные адреса, исключай секреты и персональные данные.

#### Корневой README

Содержит короткое назначение, таблицу всех существующих модулей со ссылками на их
README и статусами, ссылки на разработку и документацию Graphify. Планы можно
упомянуть отдельно, без ссылок на несуществующие модули. Не дублируй сценарии,
контракты и детали устройства каждого сервиса. Команды подробно описываются
в общей инструкции разработки, а их определения остаются в Makefile.

#### README модуля

У каждого существующего модуля, включая каркас, есть свой README.
Это краткая точка входа; заголовок — `# Модуль {name}`.
Используй пять разделов в следующем порядке:

| Раздел | Минимально достаточное содержание |
| --- | --- |
| `## Назначение и границы` | Коротко: что измеряет сервис, кто отправляет данные и за что сервис не отвечает. При необходимости поясни ключевые предметные различия. |
| `## Статус` | Что реализовано сейчас, что является только требованием или планом. Для каркаса явно укажи, что происходит при запуске. |
| `## Входы и выходы` | Реализованные интерфейсы и направления событий/метрик со ссылками на контракты. Плановые интерфейсы отмечай отдельно. Поля и JSON-примеры не дублируй. |
| `## Устройство и запуск` | Ключевые точки входа и сборки со ссылками на код, Dockerfile и общую инструкцию разработки. Только специфичные зависимости и настройки модуля. |
| `## Ограничения и дальнейшее чтение` | Существенные ограничения и ссылки на спецификацию, пояснения или общий граф. Гарантии из требований не выдавай за проверенные свойства реализации. |

Глубина README:

- Ссылки размещай рядом с соответствующими понятиями, сценариями, интерфейсами и настройками.
  Отдельный каталог уже приведённых ссылок не нужен.
- Тесты используй для проверки фактов при подготовке документации. В README модуля
  не включай отчёты о покрытии и результаты отдельных запусков; команды проверок
  описывай в общей инструкции разработки. Ссылки на тесты добавляй только если
  они необходимы для понимания существенного контракта.
- Контракты API представляй ссылками на конкретные Go-типы, обработчики и OpenAPI. Состав полей, типы,
  сигнатуры, правила валидации и JSON-примеры остаются в источниках, а не копируются в README.
- На общую архитектуру слоёв и инфраструктурные соглашения давай ссылки;
  в модуле описывай только отличия. Перечислять отсутствующие слои и механизмы не нужно.
- Алгоритмы, SQL, маппинг полей и цепочки внутренних вызовов читай в коде; сложные взаимодействия
  раскрывай в профильных документах. В README сохраняй их смысл и существенные последствия.
- Сохраняй предупреждения о безопасности, повторном выполнении, согласованности и других ограничениях,
  без которых модуль можно использовать неправильно. При сокращении оставляй краткое резюме со ссылкой.
- В README не включай хронику работы агента: перечни прочитанных файлов, даты исследования
  и результаты отдельных запусков. Порядок итогового отчёта описан ниже.
  Историю изменений функциональности отдельно не составляй без запроса.
- Mermaid-диаграмма допустима внутри одного из разделов, если объясняет специфичное для модуля
  взаимодействие понятнее и короче текста. Она заменяет соответствующее описание, а не дублирует его.
  Общую архитектуру слоёв, дерево каталогов и очевидные цепочки классов не изображай. Если подходящая диаграмма
  уже есть в профильной документации, дай ссылку на неё.
- Дополнительные разделы и примеры добавляй только по явному запросу пользователя.

Ориентир — чтение за 1–2 минуты. Больший объём оправдывают существенные особенности модуля,
а не число классов или операций. Разделы у разных модулей не обязаны иметь одинаковый объём.

#### Локальные пояснения

Раскрывай только конкретный вопрос ради которого нужен документ.
Существующие определения контрактов подключай ссылками; текстом объясняй неочевидную семантику,
условия работы и последствия отказов. Диаграммы используй для пояснения взаимодействий,
а непроверенные переходы обозначай явно. Из README должна быть ссылка на локальное пояснение.

### 4. Проверь результат

- Документация написана на русском языке.
- Пути, команды, имена пакетов и типов и ссылки существуют и актуальны; после сокращения сохранены
  используемые определения ссылок в конце Markdown-файлов.
- Существенные утверждения имеют доказательства; гипотезы и непроверенные внешние участки отмечены.
- Исторические handoff не использованы для выводов; будущие возможности не описаны как реализованные.
- Markdown корректно отформатирован.
- Документы размещены по назначению, связаны навигацией и не дублируют основное описание.
- При использовании Graphify проверены актуальность и ограничения графа; ручные выводы сохранены отдельно от отчёта.

Для корневого README проверь наличие ссылки на каждый существующий модуль и
документацию Graphify. Если граф не построен, это явно указано, а ссылок на
несуществующие результаты нет. Правила работы с графом не являются самим графом.

Для README модуля дополнительно проверь:

- Все пять разделов присутствуют в заданном порядке.
- Читатель может определить назначение, предметные понятия и границы владения данными,
  сценарии, публичные входы и выходы, устройство модуля, существенные ограничения,
  зависимости и место дальнейшего чтения.
- Каждый абзац помогает ответить на один из этих вопросов; пересказ полей, типов и шагов реализации заменён ссылками.
- Общие сведения имеют одно основное описание; история исследования осталась за пределами README.
- При сокращении сохранены существенные предупреждения, а не только навигационные ссылки.

В итоговом ответе в чате кратко укажи изменённые документы, выполненные проверки
и оставшиеся неизвестные. Полный перечень изученных файлов не требуется.
Отдельные отчёты и файлы с материалом, исключённым из README, не создавай.

Не создавай коммит и не переходи к нему без явного запроса пользователя.
