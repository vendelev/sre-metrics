# Модуль core

## Назначение и границы

Технический модуль общего HTTP-сервера и OTel-pipeline процесса: на один процесс
приходится один listener с одним `http.Server` и один `MeterProvider` с одним
`PeriodicReader` и OTLP/HTTP-экспортёром. Модуль не содержит предметной логики:
функциональные модули передают готовый `http.Handler`, View своих инструментов
и типизированные настройки и сами не открывают порты и OTel-pipeline. `core`
не импортирует функциональные модули; глобальный OTel provider не устанавливается.

## Статус

Работают HTTP-компонент — открытие и однократное закрытие listener, задача Serve
с сигнализацией ошибки, Shutdown и принудительный Close — и OTel-компонент —
Resource из стандартного `OTEL_*`-окружения, provider с View потребителя,
отключённые exemplars, экспортёр с безопасной диагностикой ошибок и однократный
Shutdown. Сборка выполняется в контейнере зависимостей dig через
[bootstrap.Provide](bootstrap/container.go). Компоненты использует
[user-login](../user-login/README.md); модуль сбора метрик пациента планируется отдельно.

## Входы и выходы

Публичная поверхность — [bootstrap](bootstrap/server.go): фасады `Server`
и `Metrics`, публикация результатов фоновых задач через [Task](bootstrap/task.go),
набор [Views](bootstrap/metrics.go) и [Provide](bootstrap/container.go) для dig;
типизированные настройки — [config](config/http.go). HTTP-компонент читает
собственное окружение ядра `CORE_HTTP_*`: слушающий адрес и тайм-ауты `net/http`,
с умолчаниями и проверками `HTTP.Validate` (`ReadHeaderTimeout ≤ ReadTimeout`,
положительность длительностей). Входы: готовый handler, корневой logger,
View инструментов. Выход: OTLP/HTTP экспорт в получатель, настроенный стандартными
`OTEL_*`; переменные функциональных модулей core не разбирает. Для интеграционных
тестов предусмотрен локальный OTLP/HTTP-получатель [oteltest](oteltest/receiver.go),
не заменяющий SDK и экспортёр подменами.

## Устройство и запуск

Внутренние реализации скрыты пакетом `internal` и доступны только через
публичную сборку: механизм listener и `http.Server` — в
[httpserver](internal/infrastructure/httpserver/server.go), provider,
экспортёр и PeriodicReader — в [otel](internal/infrastructure/otel/pipeline.go).
Контейнер только собирает объекты; фазовый протокол задаёт модуль-потребитель:
`Open` listener → `Start` pipeline → регистрация инструментов через `Meter` →
`StartServe`; остановка — `CloseListener`, HTTP `Shutdown` в переданном бюджете,
финальный `Metrics.Shutdown` с оставшимся временем. Пример координации —
[runtime.go](../cmd/user-login-httpserver/bootstrap/runtime.go) bootstrap'а
приложения. Проверки компонентов
используют настоящие listener, SDK и локальный получатель; команды — в
[инструкции разработки](../../docs/development.md).

## Ограничения и дальнейшее чтение

- Финальный экспорт — best effort: ошибка остаётся ошибкой остановки, гарантий
  доставки нет. Модуль не заводит отдельный резерв бюджета и не выполняет
  дополнительный flush — порядок задаёт владелец протокола запуска.
- Exemplars отключены общим механизмом: атрибуты запроса не переносятся
  в exemplars; имена, атрибуты и cardinality метрик остаются у функциональных
  модулей.
- Точка входа, бинарник и контейнер у модуля отсутствуют: он разделяет общий
  [Go-модуль](../go.mod) и собирается в составе приложений.
- Правила импортов между модулями — [depguard](../.golangci.yml);
  [архитектурные правила](../../.agents/rules/Architecture.md) задают границы
  слоёв и владение жизненным циклом.
