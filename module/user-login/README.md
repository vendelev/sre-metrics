# Модуль user-login

## Назначение и границы

Предназначен для измерения сценария входа в МИС по фактам от МИС и Auth:
связать события и сформировать метрики исходов и успешной длительности.
Саму аутентификацию, проверку паролей и решения о доступе сервис не выполняет.

## Статус

Работают HTTP-приём `POST /events`, предметная обработка, локальное накопление
Counter и Histogram в OpenTelemetry Go SDK `v1.47.0`, периодическое обслуживание
сценариев и штатная остановка. Компоненты собираются явной цепочкой конструкторов
в [app.go](app.go); контейнер зависимостей не используется (ревизия 2026-11-04
технического дополнения).
OTLP/HTTP-pipeline с официальным экспортёром `v1.47.0` подключён к реальному запуску:
`PeriodicReader` периодически отправляет cumulative-метрики; финальный экспорт выполняется
штатным shutdown reader на best effort — с оставшимся временем общего бюджета остановки.
Итерации 3–6 реализованы; итерация 6 (упрощение сборки и остановки) передана на ревью.
Локальный тестовый получатель не подтверждает живую интеграцию Collector/Prometheus;
приём события сам по себе не означает доставку в мониторинг.

## Входы и выходы

Внутренний [LoginObserver](internal/application/login_observer.go) принимает
предметные события и предоставляет вызываемое обслуживание. Накопление выполняет
[OTel-адаптер](internal/infrastructure/otel/recorder.go) через локальный SDK;
`PeriodicReader` собирает и экспортирует данные, не сбрасывая накопление.
`ManualReader` используется только в изолированных тестах.
Собственные memory-агрегаты и `LoginObserver.Snapshot()` удалены.
[Обработка](internal/application/process.go) ожидает
проверку входных данных вызывающим кодом; HTTP-адаптер выполняет её перед вызовом.
HTTP-адаптер записывает диагностику отрицательной длительности через явно переданный
`slog.Logger`, уже вне защищённого участка. При прямом вызове эту обязанность несёт вызывающий код.

HTTP-вход собирается в [NewHandler](internal/presentation/httpapi/handler.go): он получает
готовый `observer.Process` и логгер. Размер тела на уровне приложения не ограничивается;
сервис рассчитан на доверенных внутренних отправителей.
Готовый роутер chi регистрирует `Post("/events", ...)` и передаётся прямо в `http.Server`.
Неподдерживаемые методы обрабатывает `MethodNotAllowed` с сохранением контрактного JSON-ответа.
Правила входа и измерений определены в
[контракте событий и измерений](../../docs/specs/login-observability.md).
Согласованные технические решения всей задачи 08 и этапы их приёмки — в
[техническом дополнении](../../docs/specs/login-observability-implementation.md);
реализация отправляющей стороны не означает приёмку всей задачи 08.
Схема запроса находится в
[OpenAPI](../../docs/specs/login-observability.openapi.yml).

## Устройство и запуск

Контракты защищённого доступа находятся в [domain](internal/domain/contract/store.go),
порядок операций — в [application](internal/application/doc.go), хранение и одна
общая блокировка — в [memory](internal/infrastructure/memory/store.go).
Время операции берётся внутри защищённого участка из явно переданных часов;
положительные лимиты и готовый регистратор измерений передаются конструктору memory.
Domain определяет новые измерения через `TakeMeasurements`; успешный `Commit`
сохраняет сценарий, событие и отметки, затем под той же блокировкой вызывает
локальные `Add`/`Record`. Накопленные итоги повторно не добавляются.
SDK накапливает cumulative-ряды; удаление сценария их не уменьшает.
Сбор не является транзакционным снимком нескольких инструментов: во время обработки
Counter и Histogram могут отразить одну операцию в соседних сборах.
Сборка и порядок операций — в [app.go](app.go), задачи и общий
бюджет остановки — в [runtime.go](runtime.go), HTTP-ресурсы — в [listener.go](listener.go),
периодическое обслуживание — в [maintenance.go](maintenance.go). HTTP и обслуживание используют
один LoginObserver, одно хранилище и один экземпляр SDK. [Точка входа](cmd/main.go) обрабатывает
SIGINT/SIGTERM; при ошибке запуска или работы процесс завершается с кодом 1.
Общие ограничения слоёв — в [архитектурных правилах](../../.agents/rules/Architecture.md).

Команды сборки, требования к окружению и общие проверки — в [инструкции разработки](../../docs/development.md).
В [локальном Compose-стенде](../../docker/otel-collector/README.md) тот же сервис
называется `user-login-metrics` и собирается через [docker/metrics/Dockerfile](../../docker/metrics/Dockerfile).
API доступен доверенным отправителям как `http://user-login-metrics:8080/events`, без host-порта и маршрута Traefik.

После сборки для ручного запуска на хосте явно ограничьте адрес loopback:

```bash
USER_LOGIN_LISTEN_ADDR=127.0.0.1:8080 \
OTEL_SERVICE_NAME=mis-login-observability \
OTEL_RESOURCE_ATTRIBUTES=service.namespace=sptr,service.instance.id=user-login-local-1,host.name=node-1,deployment.environment.name=development \
OTEL_EXPORTER_OTLP_METRICS_ENDPOINT=http://localhost:4318/v1/metrics ./bin/user-login
```

Для свободного порта укажите `127.0.0.1:0`; фактический адрес выводится в JSON-логе.
Остановка в терминале — Ctrl+C. Логи идут в stderr; глобальный slog.Logger не меняется.

В контейнере умолчание `:8080` слушает интерфейсы контейнера. По BR-39 запускайте
его только в доверенной Docker-сети, **без `-p`, host networking и маршрута Traefik**:

```bash
docker network create --internal metrics-local
docker run --rm --name user-login --network metrics-local \
  -e OTEL_SERVICE_NAME=mis-login-observability \
  -e OTEL_RESOURCE_ATTRIBUTES=service.namespace=sptr,service.instance.id=user-login-local-1,host.name=node-1,deployment.environment.name=development \
  -e OTEL_EXPORTER_OTLP_METRICS_ENDPOINT=http://otel-collector:4318/v1/metrics \
  metrics-user-login:local
# В другом терминале:
docker stop --time 12 user-login
docker network rm metrics-local
```

### Настройки

[Конфигурация](internal/presentation/config/config.go) загружается один раз при старте;
разбор env по тегам полей выполняет `caarlos0/env/v11`, предметные ограничения — `Config.Validate`.
Настройки экспорта читает SDK из стандартных `OTEL_*`. Экспорт запускается после bind,
первый периодический сбор — через настроенный интервал. Примеры endpoint условные:
реальный получатель и его доступность обеспечиваются развёртыванием. Его недоступность
не мешает приёму событий, но диагностируется, включая ошибку последнего экспорта при остановке.
Пустые настройки сервиса сохраняют умолчания. Нода и окружение задаются только
через `OTEL_RESOURCE_ATTRIBUTES`. Формат адреса прослушивания
проверяется при открытии listener, а не при загрузке конфигурации.
Длительности `USER_LOGIN_*` задаются с единицей: `500ms`, `2s`, `1m`;
стандартные OTEL-интервалы и timeout — целыми миллисекундами без суффикса.

Все переменные сервиса и пример стандартных настроек SDK собраны в
[.env.example](../../.env.example). Для Compose скопируйте его в корневой `.env`:
сервис получает файл через `env_file`. Сам Go-процесс `.env` не читает;
при запуске бинарника передавайте настройки через окружение процесса.

| Env                                  | Умолчание | Назначение                                                                |
|--------------------------------------|-----------|---------------------------------------------------------------------------|
| `USER_LOGIN_LISTEN_ADDR`              | `:8080`   | Адрес `host:port`, IPv6 — `[адрес]:port`; порт 0 выбирается автоматически |
| `USER_LOGIN_MAX_SCENARIOS`            | `10000`   | Общий лимит хранимых сценариев                                            |
| `USER_LOGIN_MAX_EVENTS_PER_SCENARIO`  | `32`      | Лимит уникальных событий записи                                           |
| `USER_LOGIN_MAINTENANCE_INTERVAL`     | `1s`      | Период обслуживания                                                       |
| `USER_LOGIN_HTTP_READ_HEADER_TIMEOUT` | `1s`      | Чтение заголовков                                                         |
| `USER_LOGIN_HTTP_READ_TIMEOUT`        | `2s`      | Чтение всего запроса, включая тело                                        |
| `USER_LOGIN_HTTP_WRITE_TIMEOUT`       | `2s`      | Тайм-аут записи ответа                                                    |
| `USER_LOGIN_HTTP_IDLE_TIMEOUT`        | `30s`     | Ожидание следующего запроса keep-alive                                    |
| `USER_LOGIN_SHUTDOWN_TIMEOUT`         | `10s`     | Единый бюджет остановки                                                   |

Экспорт настраивается через `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT`,
`OTEL_EXPORTER_OTLP_METRICS_TIMEOUT`, `OTEL_METRIC_EXPORT_INTERVAL` и
`OTEL_METRIC_EXPORT_TIMEOUT`; значения для стенда приведены в `.env.example`.
При отсутствии переменных действуют умолчания SDK: интервал `60000` мс,
timeout reader `30000` мс и HTTP timeout `10000` мс. Общие `OTEL_EXPORTER_OTLP_*`
поддерживаются SDK, но соответствующие metrics-specific переменные имеют приоритет.
Для своего CA задайте `OTEL_EXPORTER_OTLP_METRICS_CERTIFICATE` с путём к доступному
PEM-файлу; в контейнере файл нужно отдельно смонтировать. Клиент и TLS настраивает SDK.

Все числовые значения положительны. Интервал обслуживания не превышает `1m`;
тайм-аут заголовков не превышает тайм-аут чтения. Перекрёстная формула бюджета остановки
относительно HTTP-тайм-аутов не проверяется: остановка короче HTTP-тайм-аутов допустима
и завершается принудительным закрытием соединений. Серверные timeout не меняют клиентский
timeout 1 с из BR-22 и не прерывают произвольную выполняющуюся Go-функцию.
Config не разбирает и не проверяет `OTEL_*`: их обработка и умолчания принадлежат SDK.
HTTPS использует проверку сертификатов. Отдельных `USER_LOGIN_*` для экспорта больше нет.

Имя сервиса задаётся через `OTEL_SERVICE_NAME`, namespace и остальные атрибуты — через
`OTEL_RESOURCE_ATTRIBUTES`, как в `.env.example`. В коде имя и namespace не фиксируются;
для существующего Collector сохраняйте `service.name=mis-login-observability`.
Нода и окружение не передаются из Config: их читает SDK из `OTEL_RESOURCE_ATTRIBUTES`.
`service.instance.id` также задаётся только через `OTEL_RESOURCE_ATTRIBUTES`;
код не генерирует ID и не добавляет значение при его отсутствии в env.
`OTEL_SERVICE_NAME` имеет приоритет над `service.name` в `OTEL_RESOURCE_ATTRIBUTES`.
Уникальность `service.instance.id` обеспечивает развёртывание: используйте новый ID
для каждого независимого экземпляра состояния, включая перезапуски.
Автоопределения ноды нет. Остальные `OTEL_*` могут влиять на работу SDK;
exemplars и View гистограммы задаются кодом. 
Секреты и персональные данные нельзя включать в Resource.
Окружение процесса не изменяется; глобальные provider, логгер и обработчик ошибок
не подменяются. Конкурентное изменение env не поддерживается.

[Prepare](internal/infrastructure/otel/recorder.go) фиксирует Resource из окружения без запуска SDK.
[StartPipeline](internal/infrastructure/otel/pipeline.go) после bind активирует тот же Recorder:
один provider, один набор инструментов/View и один `PeriodicReader`, без production-`ManualReader`.
Resource передаётся только в `Prepare`; при активации настройки экспорта читает SDK из env.
Создание reader уже запускает goroutine: владельцем становится сервис.
Reader последовательно собирает и отправляет cumulative-данные; retry и redirect
используют штатное поведение SDK и его HTTP-клиента. Последний сбор уже входит в Shutdown;
дополнительный flush не нужен. Собственного HTTP transport у приложения нет;
SDK v1.47.0 не гарантирует немедленное закрытие idle-соединений при Shutdown.
Ошибки диагностируются сервисным
логгером без тела ответа получателя; сбой не сбрасывает накопление и не блокирует приём событий.
Сохраняемой очереди и гарантии доставки нет.

### Владение ресурсами и остановка

Компоненты собираются явной цепочкой конструкторов в [app.go](app.go);
ошибки сборки останавливают запуск до открытия ресурсов. Единственный владелец
протокола — `service`: запуск, очистка частичного запуска и остановка находятся
в [runtime.go](runtime.go). Запуск: **listener → SDK/pipeline → обслуживание и HTTP →
подтверждение готовности**. Listener сначала открывается без Serve; инструменты
и шесть нулевых рядов Counter готовы до HTTP и обслуживания. Histogram появляется
только после настоящего наблюдения. Ошибка bind не запускает SDK. Ошибка запуска
pipeline освобождает listener и частично созданные SDK-ресурсы: неуспешный запуск
сам выполняет ту же процедуру очистки, что и остановка. Готовность после ошибки
не объявляется. Один последовательный цикл вызывает Maintain;
его первый вызов происходит через интервал, вызовы не перекрываются, ticker освобождается.
Ошибка HTTP, возвращённая `Serve`, или ошибка обслуживания логируется и останавливает сервис.
Ошибки `Accept` и повторные попытки обрабатывает стандартный HTTP-сервер.
Если сбой `Accept` совпал с `Shutdown`, `Serve` может вернуть `ErrServerClosed`
вместо исходной ошибки; отдельно восстанавливать её сервис не пытается.

Остановка линейна и ограничена одним общим deadline: закрыть listener для новых
соединений → отменить планирование обслуживания → выполнить HTTP Shutdown в пределах
срока, при неуспехе принудительно закрыть соединения → дождаться Serve и текущего
обслуживания в пределах того же срока → завершить SDK.
Результаты двух фоновых задач публикуются через каналы завершения; отдельной задачи
HTTP Shutdown нет. `Pipeline.Shutdown` передаётся оставшееся время: reader отменяет
периодический вызов, дожидается его завершения, выполняет последний сбор/экспорт
и завершает exporter. Даже при исчерпанном сроке команда освобождения
передаётся: вызов shutdown с истёкшим контекстом не гарантирует ни последней отправки,
ни завершения внутренней очистки SDK. Дополнительный `ForceFlush` не нужен.
HTTP timeout задаётся через `OTEL_EXPORTER_OTLP_METRICS_TIMEOUT`; повторы SDK
ограничены контекстом операции, при остановке — оставшимся общим бюджетом.

Финальный экспорт — best effort. При нештатной остановке возможна отправка неполного
накопления; последние измерения могут быть потеряны. Ошибка незавершённой обработки
сохраняется даже при успешной отправке. Повторная очистка не выдаёт новый бюджет
и не повторяет экспорт. Это не убивает зависшую Go-функцию и не гарантирует экспорт
её последующих измерений. Успешная штатная остановка возвращает nil; сбой финального
экспорта сохраняется как ошибка остановки. Гарантии доставки нет.

Контекст остановки не наследует отмену запуска; одна однократная операция остановки
сохраняет результат для повторных вызовов. Неуспешный запуск, включая отмену по сигналу,
возвращает ошибку без нормализации в успех; процесс завершается с кодом 1.

## Ограничения и дальнейшее чтение

- Состояние и SDK-накопление теряются при перезапуске. Ошибка обработки не означает общий
  rollback: самостоятельные эффекты retention и deadline сохраняются.
- `ManualReader.Collect` не выполняет обслуживание и не сбрасывает cumulative-значения.
  Локальные SDK-тесты не доказывают OTLP-доставку или представление в Prometheus.
- Counter использует `int64`, count и корзины Histogram — `uint64`, секунды и их сумма —
  `float64`. Бесконечной точности и собственной защиты от переполнения нет;
  дробные секунды могут округляться. SDK `v1.47.0` также использует внутренний `int64`
  для суммирования целочисленных значений, включая целые секунды Histogram;
  этот путь не защищён от переполнения. Числовые данные на границе экспорта
  дополнительно не проверяются: контракт инструментов и корректность регистрации
  проверяются тестами; переполненные внутри SDK значения не восстанавливаются.
- Локальный OTLP/HTTP-получатель не подтверждает живую интеграцию Collector/Prometheus:
  фактические Prometheus-имена, labels и SLI во внешнем pipeline ещё не приняты.
- [Graphify](../../graphify-out/README.md) — вспомогательная навигация;
  граф текущего проекта ещё не построен.
- [Передача событий и конфигурации: исследование hugeParam](docs/hugeparam-research.md).
- [Все модули проекта](../../README.md).
