# Файловый вход событий user-login

Файловый вход — способ передать событие без HTTP-вызова отправителя. Сервис
запускает файловый и HTTP-входы вместе.
В [Compose](../docker-compose.yml) отправитель и `user-login-metrics` монтируют один
локальный том `user-login-metrics:/mnt/metrics` и работают на одной ноде. Каталог
модуля по умолчанию — `/mnt/metrics/user-login`; его должен читать только один получатель.
`USER_LOGIN_INBOX_DIR` меняет путь, но не отключает вход. Если каталог недоступен,
сервис не начинает обслуживать запросы. Остальные [настройки](../backend/user-login/README.md#настройки)
и [команды проверки](development.md#проверка-файлового-входа-в-compose) описаны отдельно.

```text
Отправитель → запись .tmp → закрытие → rename в .json
               → чтение каталога → проверка файла, JSON и occurred_at
               → общая с HTTP очередь → воркер → локальный SDK → OTLP-экспорт
```

Файловый вход работает на Linux. Готовность означает, что каталог удалось прочитать;
завершения обработки первой пачки запуск HTTP не ждёт. Получатель сканирует каталог
при запуске и затем периодически. `fsnotify` использует inotify: переименование
в `.json` в наблюдаемом каталоге ускоряет
сканирование. Если уведомления недоступны, остаётся периодическое чтение каталога;
ошибка или переполнение watcher также вызывает повторный скан. Источник истины —
содержимое каталога, а не события watcher. За один скан файлы обрабатываются
последовательно в пределах лимита, по `mtime`, затем по имени. `mtime` задаёт
порядок и диагностический лаг, но **не возраст события**: при каждом приёме
проверяется `occurred_at` ([BR-37](specs/login-observability.md#7-частичные-данные-повторы-и-память),
от 30 минут в прошлом до 30 секунд в будущем включительно).

## Требования к отправителю

1. Один обычный файл содержит один JSON-объект в формате тела
   `POST /metrics/b/user-login/events` ([OpenAPI](specs/login-observability.openapi.yml)).
   Итоговое имя — `<event_id>.json`, где UUID — в канонической форме со строчными
   hex-символами и дефисами. Получатель проверяет формат имени, но **не сверяет**
   UUID имени с `event_id` в теле. Дедупликация использует `event_id` из тела.
2. Запишите JSON во временный файл (например, `<event_id>.tmp`) **в том же каталоге**.
   Проверьте запись и закрытие файла, затем опубликуйте его одним атомарным `rename`
   в `.json` без замены существующего файла. Если один ID могут публиковать несколько
   процессов, используйте атомарную операцию без замены (на Linux — `renameat2`
   с `RENAME_NOREPLACE`) или обеспечьте единственного писателя для ID. Не пишите
   прямо в `.json`, не дописывайте, не обрезайте и не заменяйте публикацию до её
   исчезновения. Между проверкой файла (`Lstat`) и `unlink` остаётся окно гонки:
   замена до исчезновения может привести к удалению новой версии.
3. Разрешите получателю читать файл, а отправителю и получателю — писать в каталог
   и проходить по нему; получателю также нужен листинг. Получатель сам создаёт
   подкаталог при запуске. У получателя и тестового писателя UID:GID `65532:65532`;
   при подкаталоге `0755` и корне тома `0777` другой непривилегированный UID
   не может писать в подкаталог.
   Не открывайте том недоверенным контейнерам: право записи позволяет подменять
   и удалять публикации. Не включайте в имена, содержимое или логи персональные
   данные и секреты.
4. Отправитель отвечает за ошибки записи и переименования (`ENOSPC`, права и т. п.)
   и за очистку только своих непубликованных временных файлов. Получатель
   игнорирует все расширения, кроме `.json`, и все записи, кроме обычных файлов,
   в том числе символические ссылки и каталоги. Обычный `.json` с неканоническим
   именем отклоняется и удаляется.

## Гарантии и ограничения

- При корректной постановке в очередь получатель пытается удалить файл. Если
  очередь полна или закрыта (`ErrRetry`), файл остаётся для следующего скана;
  такой повтор не расходует лимит файловых ошибок. Возраст проверяется заново,
  поэтому успевшее просрочиться событие будет отклонено.
- Невалидные публикации и публикации с исчерпанным лимитом ошибок чтения тоже
  удаляются. **Исчезновение файла — не эквивалент HTTP `202`** и не доказывает
  обработку или доставку метрик. Исход приёма отличают по диагностике.
- Если `unlink` не удался после постановки или окончательного отказа, процесс
  запоминает результат и повторяет только `unlink`, не отдавая файл обработчику
  заново. После исчерпания лимита файл остаётся, пока публикация не исчезнет
  или процесс не перезапустится. Состояние попыток — только в памяти. Если процесс
  упал между постановкой и удалением, файл, сохранившийся на томе, может быть
  прочитан повторно. После перезапуска дедупликация не восстановится, поэтому
  возможен повторный вклад; отклонённое событие также может проверяться повторно.
- Очередь, сценарии и агрегаты не персистентны. Даже если постановка и `unlink`
  прошли успешно, падение может потерять принятое, но ещё не обработанное событие
  или накопление до экспорта ([BR-32](specs/login-observability.md#7-частичные-данные-повторы-и-память)).
- Общий том — tmpfs на 256 МиБ. Содержимое теряется при рестарте ноды и при
  размонтировании tmpfs: в локальном Docker это происходит уже после отключения
  последнего активного контейнера, даже без рестарта daemon. Если второй
  контейнер продолжает держать том, остановка одного получателя том не очищает.
  Один каталог может исчерпать общий объём или число inode, и запись в других
  каталогах тоже остановится. Сумма логических размеров JSON не измеряет
  ёмкость: маленькие файлы расходуют страницы и inode; проверяйте состояние
  всей ФС через `Statfs` (например, `df -h` и `df -i`).

## Диагностика

В локальной Grafana откройте **Application → Файловый вход: диагностика**.
[Дашборд](../docker/grafana/dashboards/file-inbox.json) показывает скорость приёма
в файлах в минуту (среднее за последние 5 минут) и число файлов в каталоге на
момент последнего замера. Ниже — ошибки, возраст самого старого файла
и состояние тома. Данные можно отфильтровать по ноде и окружению; ряды без этих
меток не отображаются. Это эксплуатационная диагностика, отдельная от SLI входа.

| Ряд Prometheus | Что показывает |
| --- | --- |
| `file_inbox_events_total{outcome="accepted"}` | Число постановок в очередь, не число доставленных измерений. |
| `file_inbox_events_total{outcome="invalid_event"}` | Неправильное имя, превышение размера, отказ JSON/схемы или возраста. |
| `file_inbox_events_total{outcome="retry"}` | Число отложенных попыток, не число уникальных файлов. |
| `file_inbox_events_total{outcome="io_error"}` и `{outcome="unlink_failed"}` | Сбои операций ФС и отдельно неудачные удаления. |
| `file_inbox_files`, `file_inbox_size_bytes`, `file_inbox_oldest_file_age_seconds` | Число обычных `.json`, их логические байты и лаг по старейшему `mtime` на момент скана, до обработки пачки. |
| `file_inbox_volume_usage_ratio` | Доля занятых блоков всей ФС на Linux, включая `.tmp` и соседние каталоги; не доля занятых inode. |

Счётчик агрегирован и не подтверждает результат для отдельного ID. В предупреждениях
по файлам есть `reason`, `size`, при сбоях чтения и удаления — номер попытки и лимит;
поле `file` есть только для канонического имени. `invalid_content` объединяет отказы декодирования
и проверки возраста. Тело, исходные ошибки чтения и произвольные имена не
выводятся. Пути и имена файлов не используются в атрибутах метрик.

[Правила Prometheus](../docker/prometheus/file-inbox.rules.yml) агрегируют по
`node, environment`, без сложения повторных замеров одного тома. `FileInboxLagHigh`:
максимальный лаг выше 120 с в течение 5 мин. `FileInboxVolumeUsageHigh`:
максимальное заполнение не ниже 80% в течение 3 мин. Для обоих нужны непустые
`node` и `environment`. Эти алерты не изменяют формулы SLI входа.
