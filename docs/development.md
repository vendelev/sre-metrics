# Разработка Metrics

## Окружение

Для Compose скопируйте корневой [.env.example](../.env.example) в `.env` и настройте
значения под своё окружение. Существующий `.env` не перезаписывайте; файл исключён из Git.
Compose передаёт его сервису `user-login-metrics` через `env_file`.
При прямом запуске Go-бинарник файл не читает: переменные должны быть в окружении процесса.

Версия Go указана в [go.mod](../backend/go.mod); образ сборки в
[Dockerfile сервиса](../docker/metrics/Dockerfile) должен соответствовать ей.
Для линтера требуется golangci-lint v2, для образа — Docker с доступным daemon.
Проверка с race detector требует поддерживаемой Go платформы и C-компилятора.
Команды выполняются из корня репозитория.

Для форматирования нужны `golines` (поддерживаемый форк `golangci/golines`)
и `goimports`, доступные в `PATH`:

```bash
go install github.com/golangci/golines@latest
go install golang.org/x/tools/cmd/goimports@latest
export PATH="$(go env GOPATH)/bin:$PATH"
```

## Команды

Определения поддерживаются в [Makefile](../Makefile):

```bash
make build-user-login  # bin/user-login-server
make test              # тесты поведения с покрытием и race detector
make lint              # включая архитектурные импорты
make lint-fix          # golines/goimports, затем автоисправления golangci-lint
```

`make build-user-login`, `make test` и `make lint` не исправляют исходники;
`make lint-fix` изменяет Go-файлы во всём `backend/`, включая форматирование,
импорты и доступные линтеру автоисправления. Перед проверками запускайте `make lint-fix`.

Сборка без Make:

```bash
go -C backend build -o ../bin/user-login-server ./cmd/user-login-httpserver
docker build -f docker/metrics/Dockerfile -t metrics-user-login:local .
```

Состояние и поведение запуска описаны в [README модуля](../backend/user-login/README.md).
Успешная сборка не означает запуск сервера или работу экспорта.
HTTP-контракт проверяется через `httptest`; обычный набор тестов также проверяет lifecycle
на `127.0.0.1:0` без внешних зависимостей. OTLP/HTTP-тесты используют локальный `httptest`,
разбирают официальный protobuf, проверяют отказ/восстановление, timeout, retry, redirect,
отказ недоверенного TLS и приём сертификата CA через стандартное окружение SDK;
периодичность reader проверяется с `synctest` и управляемым экспортёром.
Интегрированный запуск проверяется с настоящим HTTP-получателем: приём событий,
восстановление накопления, последний пакет после успешного завершения обработки и ошибка
незавершённого drain при обычном Shutdown SDK с возможной последней отправкой.
Обычные сервисные тесты используют настоящие listener, SDK и OTLP/HTTP-экспортёр
с локальным получателем; фабрики запуска и подмена pipeline в сервисе не предусмотрены.
Отмена между внутренними фазами проверяется отдельно от полного запуска.
Общий бюджет ожидания задач проверяется с синтетическим временем, а оставшийся
бюджет настоящего экспорта после завершения обслуживания — через локальную сеть.
Это не проверка МИС/Auth или живого Collector/Prometheus. В реальном запуске используется
один `PeriodicReader`; локальный `ManualReader` сохранён только для изолированных тестов.

Объединённое покрытие учитывает код, вызываемый тестами других пакетов:

```bash
go test -race -coverpkg=./... -coverprofile=/tmp/opencode/metrics-coverage.out ./...
go tool cover -func=/tmp/opencode/metrics-coverage.out
golines --base-formatter=goimports -m 120 --dry-run .
git diff --check
```

Каталог для временного профиля при необходимости создайте заранее. Порог покрытия проекта — 75%;
процент не заменяет проверку поведения. `golines --dry-run` показывает предлагаемые
изменения без записи файлов.
Длинные строковые литералы и комментарии могут остаться без переноса.

Документацию Go-пакетов можно просматривать локально через `pkgsite`:

```bash
go install golang.org/x/pkgsite/cmd/pkgsite@latest
pkgsite -http=127.0.0.1:6060 .
```

Из корня проекта команда запускает сервер документации. Пакет сервиса доступен
по адресу <http://localhost:6060/github.com/vendelev/sre-metrics/backend/user-login>.
При запуске в WSL адрес можно открыть в браузере Windows; остановка — Ctrl+C.

Для ручной проверки запустите бинарник по инструкции сервиса.

Endpoint, HTTP timeout, TLS и период экспорта задаются стандартными `OTEL_*`;
готовый пример — в [.env.example](../.env.example), пояснения — в
[README user-login](../backend/user-login/README.md#настройки).
Нода и окружение задаются через `OTEL_RESOURCE_ATTRIBUTES`.
Длительности OTEL задаются целыми миллисекундами, длительности `USER_LOGIN_*`
и `CORE_HTTP_*` — с единицами.

В другом терминале отправьте синтетическое событие с текущим UTC-временем.
Пример для GNU date:

```bash
occurred_at=$(date -u +%Y-%m-%dT%H:%M:%S.%3NZ)
curl --max-time 3 -i http://127.0.0.1:8080/metrics/b/user-login/events \
  -H 'Content-Type: application/json' \
  --data-binary "{\"event_id\":\"019aabcd-0000-7000-8000-000000000001\",\"scenario_id\":\"019aabcd-0000-7000-8000-000000000100\",\"occurred_at\":\"$occurred_at\",\"source\":\"mis\",\"type\":\"login_started\"}"
```

Ожидается 202 без тела: событие принято в очередь, обработка ещё не подтверждена.
При полной очереди ожидается 503 с кодом overloaded.
Получатель OTLP должен быть настроен отдельно; его недоступность
не меняет HTTP-ответ, но приводит к диагностике экспорта. Затем остановите процесс Ctrl+C:
при успешном завершении
появляется сообщение о штатной остановке и процесс возвращает код 0.
Это проверяет приём, а не обработку или OTLP-доставку. Для нового синтетического события
меняйте event_id; повтор использованного ID с другим временем конфликтует при обработке,
но не меняет ответ 202. Ошибка последнего
экспорта означает неуспешную остановку; исправный HTTP-приём сам по себе не гарантирует код 0.

При контейнерной проверке отправляйте тот же запрос из вспомогательного контейнера
в сети сервиса, например `docker run --rm --network metrics-local curlimages/curl ...`
с URL `http://user-login:8080/metrics/b/user-login/events`. Порт на хост не публикуется; параметры сети
и остановки приведены в README сервиса. Для повторяемой проверки фиксируйте тег
или digest вспомогательного образа. После проверки удалите только созданные тестовые ресурсы.

Готовая Compose-конфигурация, DNS-имена сервисов, подключение правил Prometheus
и дашбордов описаны в [инструкции локального стенда](../docker/otel-collector/README.md).
В этом стенде адрес API — `http://user-login-metrics:8080/metrics/b/user-login/events`, сеть отправителей — `sptr_all`.
Пример выше с `user-login` и `metrics-local` относится к отдельному ручному запуску контейнера.

### Проверка HTTP-приёма

На отдельном тестовом стенде запустите `bash test.sh`. Скрипт отправляет
синтетические события, которые могут повлиять на метрики и SLI. Он проверяет
приём (`202` без тела) и ответы на ошибки входной валидации, а по логам получателя
подтверждает конфликты и отклонения после закрытия сценария по сроку.
Доставку и значения метрик нужно проверять отдельно.

Для нестандартных `DOCKER_NETWORK` или `EVENTS_URL` задайте `LOG_CONTAINER`
именем или ID контейнера того же получателя. Без него на нестандартном стенде
проверяются только HTTP-ответы; `LOG_CONTAINER=` явно отключает проверку логов.
`bash test.sh --limits` требует логи и дополнительно проверяет лимит событий
одной записи. Если `USER_LOGIN_MAX_EVENTS_PER_SCENARIO` на стенде отличается
от 32, передайте то же значение в `MAX_EVENTS_PER_SCENARIO`.

### Проверка файлового входа в Compose

Проверяйте только на отдельном тестовом стенде: сценарий синтетический, но может
повлиять на измерения входа. Штатный Compose использует фиксированные имена
контейнеров, поэтому одного `-p` недостаточно для изоляции от уже работающего
стенда. В этом случае используйте отдельный Compose-файл без фиксированных имён,
с отдельными сетью и tmpfs-томом. Сохраните имена сервисов `user-login-metrics`
и `user-login-inbox-writer`, общий mount `/mnt/metrics` и настройки UID:GID
из [Compose](../docker-compose.yml). Выберите его через `COMPOSE_FILE` и
`COMPOSE_PROJECT_NAME`. Не меняйте `.env` рабочего стенда.

Запустите **тестовый** получатель через Compose с каталогом файлового входа
по умолчанию (`/mnt/metrics/user-login`). Дождитесь сообщения `сервис user-login запущен`.
Писатель из профиля `file-inbox` запускается разово самим скриптом,
без запуска зависимостей и без host-портов.

```bash
docker compose --profile file-inbox config -q  # Только проверка, не выводит значения env
bash -n test.sh
bash test.sh --inbox
```

В режиме `--inbox` скрипт не вызывает `curl` и не перезапускает сервисы. Он ждёт удаления файлов
и проверяет безопасные логи по тестовым UUID. Конфликт второго начала с первым
подтверждает, что воркер получил и сохранил валидное начало. Битый JSON и
событие с `occurred_at` на 31 минуту в прошлом должны быть отклонены; оба файла
созданы во время теста. Это не проверка доставки метрик. Скрипт не удаляет
опубликованные файлы при тайм-ауте. После проверки удаляйте только ресурсы
тестового проекта.

Для проверки обоих входов запустите `bash test.sh --mixed`. Скрипт публикует
начала и завершения файлами, а варианты входа — по HTTP с тем же `scenario_id`.
По логам получателя проверяются обработка первого успешного сценария и отказ
добавить новый факт к `unknown`. Если переопределяете `DOCKER_NETWORK` или
`EVENTS_URL`, укажите сеть и адрес того же получателя.

Ожидаемый вклад: 33 принятых файла, 12 успехов, 2 технические ошибки, 2 отказа
и 1 `unknown`. Для `credentials` и `existing_session` ожидается по 6 измерений
успешной длительности: 2, 5, 6, 30, 31 и 61 с. Для графиков прироста в Grafana
дождитесь исходного сбора Prometheus до запуска и следующего сбора после экспорта.
Скрипт метрики не проверяет.

На изолированном стенде Linux в WSL (Docker 29.6.1, Compose 5.3.0) подтверждены
создание подкаталога `0755` и удаление публикаций получателем `65532:65532`.
Писатель с тем же UID:GID смог публиковать, UID `65533` — нет, хотя корень
тома имел `0777`. С интервалом сканирования `5m` сценарий `--inbox` завершился
за 5 с благодаря уведомлениям. В отдельной проверке с двумя файлами до запуска
получателя и лимитом `1` файл на скан первый удалился при старте, второй — на
первом тике `12s`, без новых публикаций. Изолированные Collector и Prometheus
получили все диагностические ряды, в том числе `accepted=2` (начало и проба)
и `invalid_event=2`. Реальные МИС/Auth, внешний pipeline и срабатывание алертов
на живом трафике эта проверка не покрывает. Имена рядов и пороги —
в [описании файлового входа](file-inbox.md#диагностика).

## Зависимости и организация

Версии Go-зависимостей и их контрольные суммы находятся в
[`../backend/go.mod`](../backend/go.mod) и [`go.sum`](../backend/go.sum). Путь Go-модуля
`github.com/vendelev/sre-metrics` соответствует адресу репозитория. При переименовании
обновляются `../backend/go.mod`, Go-импорты и пути в [.golangci.yml](../backend/.golangci.yml).

При добавлении сервиса следуйте
[правилам его размещения и изоляции](../.agents/rules/Architecture.md#статус-и-границы-сервисов).
Дополните каталог модулей в корневом README, команды сборки в Makefile
и правила импортов в `../backend/.golangci.yml`.

Правила [архитектуры](../.agents/rules/Architecture.md) и
[тестирования](../.agents/rules/Testing.md) определяют границы и требования к проверкам.
Ограничения на секреты и персональные данные — в [AGENTS.md](../AGENTS.md#документация).
