# user-login: согласованные технические решения задачи 08

- Статус решений: **согласовано пользователем**.
- Дата фиксации: 2026-11-04; ревизия упрощения сборки и остановки — той же датой.
- Область: пересмотр технической реализации задачи 08 целиком. Ревизия 2026-11-04
  заменяет сборку через Fx и бюджет остановки с резервом SDK на явную сборку
  конструкторами и единый бюджет (раздел 8).
- Основной бизнес-контракт: [login-observability.md](login-observability.md), редакция 0.30.
- Согласование решений не означает завершённую реализацию, приёмку всех итераций или разрешение выполнить их одновременно.

## 1. Назначение и приоритет

Документ фиксирует решения, принятые после первоначальной постановки задачи 08:
способ накопления измерений, сборку, жизненный цикл, конфигурацию и экспорт.
Он конкретизирует технические вопросы OQ-10 и раздела 8 основной спецификации.
Бизнес-правила, OpenAPI, формулы SLI, SLO и приложения Prometheus не изменяются;
редакция комплекта 0.28 из-за этого дополнения не повышается.

Для реализации используйте бизнес-контракт вместе с этим дополнением и постановкой
текущей итерации. При расхождении с первоначальным техническим предложением задачи 08
действуют решения этого документа. Постановка итерации ограничивает объём работ,
но сама по себе не меняет согласованные решения.

Фактическое устройство и команды запуска описываются в
[README сервиса](../../module/user-login/README.md), общие ограничения слоёв — в
[архитектурных правилах](../../.agents/rules/Architecture.md).
Технические детали SDK проверяются по документации и исходникам закреплённой версии,
а не выводятся из общих примеров для других версий.

### HTTP-маршрутизация

По решению пользователя используется `github.com/go-chi/chi/v5`; версия закрепляется
в `go.mod`. HTTP-адаптер возвращает готовый роутер с `Post("/events", ...)`, без собственного
типа `Handler` и дополнительного `http.ServeMux` в сборке. Выбор пути и метода выполняет chi;
`MethodNotAllowed` сохраняет JSON `method_not_allowed`, `Allow: POST` и отсутствие тела для HEAD.
Проверка MIME-типа остаётся через `mime.ParseMediaType`: штатный `AllowContentType` пропускает
пустое тело и не проверяет корректность параметров MIME. Бизнес-контракт и OpenAPI не меняются.
Регистрируется точный путь `/events`; дополнительные пути, нормализация слешей и редиректы
не добавляются. Неизвестные пути для поддерживаемых chi методов получают штатный 404.

## 2. Что заменено и что сохранено

| Первоначальное решение или требование задачи 08                | Согласованная замена                                                                            |
|----------------------------------------------------------------|-------------------------------------------------------------------------------------------------|
| Прямая сборка через Dig, вручную организованный жизненный цикл | Явная сборка конструкторами в корневом пакете, без контейнера (Dig, Fx); ревизия 2026-11-04     |
| Бюджет остановки с гарантированным резервом OTel (10s = 7s + 3s) | Один общий deadline остановки; финальный экспорт — best effort с оставшимся временем (ревизия 2026-11-04) |
| Собственные накопленные суммы и корзины в memory               | Накопление Counter и Histogram внутри OTel SDK                                                  |
| Экспорт готового `observer.Snapshot()`                         | Регистрация только новых измерений через SDK `Add` и `Record`; собственный `Snapshot` удаляется |
| Внешний предагрегированный `Producer`                          | Обычные синхронные SDK-инструменты; `Producer` не нужен                                         |
| Генерация ID экземпляра в коде                                 | По решению пользователя ID задаётся только в `OTEL_RESOURCE_ATTRIBUTES` |
| Собственные запреты OTLP retry и HTTP redirect                 | По решению пользователя используются штатные retry SDK и redirect его HTTP-клиента |

Прежний запрет повторно добавлять **полное накопленное значение** сохраняется.
Запрет использовать `Add`/`Record` как таковые больше не применяется: ими регистрируются
только новые измерения, один раз. Готовые корзины не восстанавливаются повторными наблюдениями.

Не меняются дедупликация, окончательность исходов, позднее дополнение измерений,
самостоятельные эффекты deadline/retention, обработка отрицательной длительности,
ограничения памяти и HTTP-ответы. Сбой экспорта не влияет на результат приёма события.
Термин для регистрируемых данных в реализации и пояснениях — **«измерения»**.

Причина замены накопителя: использовать штатное накопление SDK вместо сопровождения
собственных сумм, корзин и преобразования готовых агрегатов. Распознавание нового
измерения остаётся обязанностью предметного кода: SDK не знает правил сценариев и повторов.

## 3. Регистрация и согласованность

Целевой путь данных:

```text
HTTP → application/domain → memory.Commit
                              ↓ новые измерения
                         OTel-адаптер
                              ↓ Add / Record
                         OTel SDK
                              ↓ PeriodicReader
                     официальный OTLP/HTTP exporter
```

Domain формирует новые измерения через `TakeMeasurements` и хранит признаки уже
выданных измерений. Независимый от SDK контракт регистрации находится в domain;
его реализует `internal/infrastructure/otel/`. Memory получает регистратор явно.
Application и domain не импортируют SDK или конкретный memory-адаптер.

В успешном `Commit` все проверки предшествуют изменениям. Затем под существующей
блокировкой сохраняются сценарий, событие и отметки, после чего синхронно регистрируются
новые измерения в SDK. Регистратор не выполняет сеть, не запускает задачи и не обращается
обратно к Store. Инструменты готовы до обработки первого события.
Локальные `Add`/`Record` не возвращают ошибок; SDK не предоставляет отката этих операций.

Сетевой экспорт не удерживает блокировку состояния и не является условием HTTP 204.
Удаление сценария не удаляет накопление SDK. Второй собственный накопитель и история
наблюдений для повторного воспроизведения не вводятся.

**Принятый компромисс:** SDK-сбор не является транзакционным снимком нескольких
инструментов. Counter и Histogram могут отразить одну операцию в соседних сборах.
Это не новый исход, не повторная регистрация и не сброс накопления. После подтверждённого
завершения обработки последний сбор должен включать все завершённые измерения.
Гарантия общего атомарного снимка всех семейств из первоначального подхода не переносится
на этот вариант.

## 4. SDK и инструменты

Согласованная версия: **OpenTelemetry Go v1.47.0** (ревизия 2026-11-04 убирает Uber Fx).
Версии фактически подключённых модулей фиксируются в [go.mod](../../module/go.mod)
и [go.sum](../../module/go.sum). Официальный HTTP-экспортёр подключается на этапе экспорта,
а не как часть локального накопления.

Имена, единицы, атрибуты и значения берутся из
[раздела 8 бизнес-контракта](login-observability.md#8-минимальные-метрики).
Используются `Int64Counter` для двух счётчиков и `Float64Histogram` для длительности.
Каждое новое завершение или классифицированная ошибка регистрируется через `Add(1)`,
длительность — одним `Record(duration.Seconds())`.

До обработки событий через `Add(0)` создаются четыре ряда исходов и два ряда ошибок.
Это не создаёт сценариев. Histogram не заполняется искусственным наблюдением нуля;
реальная длительность ноль допустима. До первого наблюдения Histogram может отсутствовать.

Явный SDK View задаёт границы **5, 30, 60 секунд** и отключает min/max.
Exemplars отключены. SDK сам вычисляет count, sum и непересекающиеся корзины.
Накопительные Prometheus buckets формируются позднее в pipeline, не в Go-адаптере.
Все суммы и Histogram экспортируются с **cumulative temporality**, выбранной
через стандартное окружение SDK (см. раздел 6).

При локальной итерации используется зарегистрированный `ManualReader`: он позволяет
проверять настоящее накопление без сети и планировщика. Provider без reader не заменяет
накопитель. Для целевого экспорта используется `PeriodicReader`; второй scheduler
поверх него не создаётся. Временный `ManualReader` не должен случайно остаться вторым
независимым production-потоком сбора при подключении периодического экспорта.

### Числовые ограничения

Преобразования накопленного `uint64` в Counter больше нет: Counter принимает единичные
измерения. Это не устраняет ограничения SDK: Counter использует `int64`, count и корзины
Histogram — `uint64`, длительность и сумма секунд — `float64`. Округление возможно;
бесконечная точность и защита от любого переполнения не обещаются.

Контракт инструментов и корректность регистрации проверяются тестами. Собственная
производственная проверка числовых данных на границе экспорта не выполняется
(ревизия 2026-11-04); переполненные внутри SDK значения не восстанавливаются.
Некорректные данные не заменяются нулями. Собственные дублирующие накопленные
счётчики ради такой проверки не вводятся.

## 5. Resource, scope и временные метки

Состав Resource определяет основная спецификация. Способ получения значений:

| Атрибут | Источник |
| --- | --- |
| `service.namespace` | `OTEL_RESOURCE_ATTRIBUTES`; в `.env.example` задано `sptr` |
| `service.name` | `OTEL_SERVICE_NAME` либо `service.name` в `OTEL_RESOURCE_ATTRIBUTES`; в примере `mis-login-observability` |
| `service.instance.id` | Только `OTEL_RESOURCE_ATTRIBUTES`, без генерации или запасного значения в коде |
| `host.name` | Только `OTEL_RESOURCE_ATTRIBUTES` |
| `deployment.environment.name` | Только `OTEL_RESOURCE_ATTRIBUTES` |

По решению пользователя настройки Resource вынесены в корневой `.env.example`,
а стандартное окружение SDK больше не переопределяется значениями из кода.
По решению пользователя генерация UUID удалена. Если ID не задан через env,
приложение не добавляет этот атрибут. Уникальность ID для каждого экземпляра состояния,
включая перезапуски, обеспечивает развёртывание; ID не используется как имя ноды.
Независимые экземпляры имеют независимые накопления. Имена нод должны быть уникальны внутри
инсталляции и стабильны при замене контейнера; правильность этих значений обеспечивает развёртывание.

Resource задаётся явно, автоматическое определение hostname контейнера не используется.
Scope имеет постоянное техническое имя без динамических атрибутов. Во всех частях метрик
запрещены ID событий/сценариев, пользовательские данные, cookies, токены, URL запросов
и тексты ошибок. Исходные OTel-имена не получают Prometheus-суффиксов.

Временные метки формирует SDK. Инструменты создаются до обработки событий;
cumulative start timestamps стабильны при следующих сборах. Позднее появление варианта
или Histogram не пересоздаёт provider и не сбрасывает другие ряды.
Начальные метки разных инструментов могут немного различаться из-за времени их создания;
это не означает разные процессы. Экспериментальный режим start timestamps на отдельный
поздно появившийся ряд не включается.

## 6. Конфигурация целевого экспорта

По решению пользователя endpoint, timeout, TLS и период экспорта переданы стандартному
окружению SDK; собственные `USER_LOGIN_OTLP_*` и `PipelineSettings` удалены.
Настройки сервиса читает `presentation/config`, настройки экспорта — SDK при активации.
Таблица ниже — согласованный контракт. Фактически подключённые настройки описаны
в [README сервиса](../../module/user-login/README.md#настройки).

| Env | Умолчание | Назначение |
| --- | --- | --- |
| `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` | Умолчание SDK | Полный URL с путём `/v1/metrics` |
| `OTEL_EXPORTER_OTLP_METRICS_TIMEOUT` | `10000` мс | Timeout HTTP-клиента SDK |
| `OTEL_EXPORTER_OTLP_METRICS_TEMPORALITY_PREFERENCE` | `cumulative` | Temporality SDK; для текущего контракта в окружении задаётся `cumulative` |
| `OTEL_METRIC_EXPORT_INTERVAL` | `60000` мс | Интервал периодического экспорта |
| `OTEL_METRIC_EXPORT_TIMEOUT` | `30000` мс | Timeout reader; при Shutdown с deadline используется контекст вызывающего |
| `OTEL_EXPORTER_OTLP_METRICS_CERTIFICATE` | Не задан | Путь к PEM-файлу CA, читаемому SDK |
| `USER_LOGIN_SHUTDOWN_TIMEOUT` | `10s` | Единый бюджет остановки сервиса; отдельный резерв OTel отсутствует (ревизия 2026-11-04) |

Длительности сервиса положительны и задаются с единицей; длительности SDK — целыми
миллисекундами без суффикса. Обработку и умолчания `OTEL_*` определяет SDK, не `Config.Validate`.
Тайм-аут чтения заголовков не превышает тайм-аут чтения. Перекрёстная
формула бюджета остановки относительно HTTP-тайм-аутов не проверяется (ревизия
2026-11-04): HTTP-тайм-ауты ограничивают сетевые операции, а не произвольный обработчик;
остановка короче HTTP-тайм-аутов допустима и завершается принудительным закрытием
соединений. По решению пользователя собственные поля ноды и окружения, их проверка
в Config и тип ResourceSettings удалены. Атрибуты места запуска задаются только
через `OTEL_RESOURCE_ATTRIBUTES`, без запасных значений в коде приложения.
Endpoint и его обработка принадлежат SDK; собственной проверки URL нет.

Условный пример для доверенной Docker-сети — `http://otel-collector:4318/v1/metrics`.
Он не подтверждает существование DNS-имени, доступность Collector или правильность deployment.
HTTP разрешён; для HTTPS проверка сертификатов остаётся включённой с системными
доверенными CA либо CA из стандартного окружения SDK. В контейнере файл CA
нужно отдельно смонтировать. Собственная загрузка `.env` и hot reload не добавляются.

### Настройки сервиса и SDK

По решению пользователя стандартные `OTEL_*` определяют endpoint, timeout, TLS,
период экспорта и атрибуты Resource. Metrics-specific переменные экспортёра имеют
приоритет над общими. Собственный HTTP-клиент и запреты retry/redirect удалены.
Exemplars и явный View гистограммы задаются кодом. По решению пользователя
temporality передана SDK: в `.env.example` задано
`OTEL_EXPORTER_OTLP_METRICS_TEMPORALITY_PREFERENCE=cumulative`.
Соблюдение BR-41 и AC-30 обеспечивает развёртывание; приложение не проверяет
и не переопределяет эту переменную. Другие значения не соответствуют текущему контракту.
По решению пользователя selector агрегации экспортёра и лимит кардинальности
больше не переопределяются приложением: их определяет SDK, включая стандартное
окружение. View сохраняет явную агрегацию Histogram независимо от предпочтения
экспортёра. Достаточный лимит кардинальности для сохранения контрактных рядов
обеспечивает развёртывание; слишком малый `OTEL_GO_X_CARDINALITY_LIMIT` объединяет
измерения в overflow с потерей атрибутов. Остальные стандартные переменные
обрабатывает SDK.

Процессное окружение не очищается и не изменяется ради обхода чтения env библиотекой.
Глобальные provider, логгер и error handler не подменяются.

В SDK v1.47.0 `WithResource` объединяет переданный Resource с `resource.Environment()`.
В `WithResource` передаётся Resource из `resource.Environment()`;
атрибуты не генерируются и не задаются кодом приложения.
Настройка окружения должна сохранять запрет ID событий/сценариев, секретов и
персональных данных в метриках. HTTP-клиент и transport создаёт SDK;
полная поддержка всех стандартных переменных выбранным pipeline не обещается.

## 7. Экспорт, ошибки и доставка

Используется официальный `otlpmetrichttp` с protobuf, а не собственный OTLP-клиент.
`PeriodicReader` выполняет периодический сбор и экспорт; первый периодический сбор —
после интервала. Интервал 10 секунд означает планирование, не гарантию доставки
строго каждые 10 секунд. Отправки не перекрываются.

**OTLP retry использует штатное поведение SDK.** Redirect выполняется штатным
HTTP-клиентом SDK. BR-21 отдельно определяет однократную отправку событий МИС/Auth,
а не политику доставки метрик.
Ошибка или timeout отправки не останавливают HTTP-приём, не меняют результат `Process`
и не обнуляют SDK. Следующий успешный цикл отправляет актуальное накопление процесса.
Успешная отправка также не обнуляет cumulative-значения.

Во время отправки новых измерений продолжают регистрироваться. Отправляемый пакет —
результат конкретного сбора, а последующие изменения становятся видимы в следующем пакете.
Сохраняемой очереди, истории событий и гарантированной доставки нет. Перезапуск теряет состояние.

Ошибки диагностируются через переданный сервисный логгер. Тонкая обёртка официального
экспортёра может сохранить исходную ошибку для SDK; стандартная диагностика SDK при этом
может дополнительно появиться в stderr. Собственный глобальный error handler ради
устранения этого вывода не устанавливается.

## 8. Сборка, запуск и завершение

Ревизия 2026-11-04 заменяет Fx и бюджет остановки с резервом SDK. Сборка выполняется
явной цепочкой конструкторов в корневом пакете; контейнер зависимостей (Dig, Fx)
и его lifecycle не используются. Один компонент корневого пакета владеет ресурсами
и последовательностью внутренних фаз. `Run(ctx)` сохраняется, сигналы и код завершения
принадлежат `cmd`. Внутренние компоненты не получают обвязку сборки; технические
функции lifecycle могут находиться в других файлах того же корневого пакета.

При `PeriodicReader` конструктор уже запускает goroutine, поэтому запуск выполняется
после полной сборки:

1. Открыть listener, не начиная обработку запросов.
2. Создать и запустить OTel pipeline, подготовить инструменты и нулевые Counter.
3. Запустить HTTP Serve и обслуживание; подтвердить готовность.

Ошибка bind не запускает reader; последующая ошибка инициализации освобождает
listener. Каждый созданный SDK-ресурс сразу получает владельца и путь очистки.
Неуспешный запуск сам выполняет ту же процедуру очистки, что и остановка, и
возвращает ошибку; специальная нормализация отмены запуска в успех не выполняется.
Отмена до начала запуска может завершаться штатно. После ошибки или отмены
готовность не объявляется; контекст запуска не становится контекстом срока жизни задач.

Целевой порядок остановки — один общий deadline без резерва SDK:

1. Прекратить приём новых запросов и отменить планирование обслуживания.
2. Выполнить HTTP `Shutdown` в пределах срока. При неуспешном `Shutdown` выполняется
   принудительный `Close`; ошибка завершения сохраняется.
3. Дождаться фоновых задач в пределах того же срока.
4. Завершить SDK обычным `Shutdown` с оставшимся временем. Даже при исчерпанном
   сроке передаётся команда освобождения ресурсов.

Периодическая и последняя отправки согласуются через штатный shutdown reader.
В проверенной версии `PeriodicReader.Shutdown` останавливает периодический цикл,
дожидается его завершения, выполняет последний сбор/экспорт и закрывает exporter.
Дополнительный `ForceFlush` механически не добавляется. Сам факт вызова `Shutdown`
с истёкшим контекстом не подтверждает завершение очистки: поведение проверяется
для закреплённой версии SDK, ограничения явно отражаются в результате и документации.
Сетевой timeout и оставшийся общий бюджет ограничивают отправку.

Финальный экспорт — best effort с оставшимся временем. При нештатной остановке
возможна отправка неполного накопления; последние измерения могут быть потеряны.
Доставка не гарантируется. Ошибка незавершённой обработки сохраняется даже при
успешной отправке: остановка остаётся неуспешной. Произвольную зависшую Go-функцию
нельзя насильно завершить контекстом; остановка SDK не означает её завершения и
не гарантирует экспорт её последующих измерений. Повторная очистка не выдаёт новый
бюджет и не повторяет экспорт. Даже успешный финальный экспорт не подтверждает
scrape последнего значения Prometheus.

Контекст остановки независим от отменённого контекста работы; повторная очистка
не обновляет бюджет. Это требования к поведению, а не к конкретным вспомогательным
функциям или их количеству.

Ошибка HTTP/обслуживания инициирует остановку с сохранением причины. Остановка
и очистка неуспешного запуска используют один и тот же протокол с общим бюджетом.
Фактическое владение ресурсами описано в README сервиса.

Согласованное упрощение: результат HTTP определяется стандартным `http.Server.Serve`,
собственного перехвата и классификации ошибок `Accept` нет. При совпадении сбоя
`Accept` с `Shutdown` сервер может вернуть `ErrServerClosed` вместо исходной ошибки;
в таком случае штатная остановка не превращается в ошибку ради восстановления причины.

## 9. Итерации и состояние принятия

Срез состояния на дату фиксации; незакоммиченный код сам по себе не означает приёмку.

| Итерация | Объём | Состояние |
| --- | --- | --- |
| 1. Fx | Переход с прямого Dig, lifecycle и ошибки запуска | Реализована и принята после исправления отмены bind |
| 2. Локальный SDK | Регистрация измерений, удаление собственных агрегатов, `ManualReader` | Реализована и согласована пользователем; полное координационное ревью в этой сессии не проводилось |
| 3. OTLP/HTTP и config | Env, полный Resource, официальный exporter, периодичность, timeout | Реализована и передана на ревью; приёмка не объявлена |
| 4. Экспорт в Fx | Startup/cleanup, завершение обработки до последнего экспорта, резерв бюджета | Реализована и передана на ревью; приёмка не объявлена. Экспорт подключён к запуску сервиса |
| 5. Итоговая проверка | Все команды, покрытие, документация, сводка для сквозной приёмки | Предстоит |
| 6. Упрощение сборки и остановки | Ревизия 2026-11-04: явная сборка без Fx, единый бюджет остановки без резерва SDK, best-effort финальный экспорт, удаление нормализации отмены запуска и числовой проверки экспорта | Реализована и передана на ревью; приёмка не объявлена |

Итерации 3 и 4 — части одной целевой архитектуры; промежуточный код не должен объявляться
полностью настроенным сервисом до подключения согласованного lifecycle.
Проверенная живая интеграция Collector/Prometheus и изменения внешнего pipeline —
отдельный этап приёмки. Инструментирование МИС/Auth не входит в задачу 08.

## 10. Проверки и границы подтверждения

| Уровень | Минимальное подтверждение |
| --- | --- |
| Локальные OTel-данные | Настоящие application + memory + SDK: контракт, нули, обе разновидности, реальные 0/5/30/60 и значения выше границ, повторный сбор, поздние измерения, Resource, времена, отсутствие ID/секретов |
| OTLP/HTTP | Локальный получатель разбирает официальный protobuf: путь, данные, отказ/восстановление, cumulative, timeout, отсутствие retry и влияния на HTTP-приём |
| Lifecycle | Явная сборка, частичный запуск с самостоятельной очисткой и сохранением исходной ошибки, единый бюджет остановки, ожидание активного запроса при успешном завершении, прекращение обслуживания, попытка финального экспорта при наличии времени, безопасное завершение при недоступном получателе, повторная очистка без нового бюджета и экспорта |
| Живой pipeline | Фактические имена Prometheus, преобразование Resource в `node`/`environment`, различимость экземпляров, buckets, reset, baseline и правила SLI |

Для локальных тестов используют явные сигналы, управляемые зависимости и подходящий
`synctest`, а не случайные ожидания через `Sleep`. Предметные переходы не дублируются
ради покрытия SDK. Тесты живого pipeline запускаются отдельно и явно.

Для реализации выполняются `make build`, `make test` с race detector, `make vet`,
`make lint`, `make image-user-login`, проверка форматирования и объединённого покрытия
с порогом 75%. Команды и окружение — в [инструкции разработки](../development.md).
При отсутствии Docker фиксируется ограничение, окружение без согласования не меняется.

Для итерации 1 координатор подтвердил build, тесты с race detector, vet, lint,
форматирование и `git diff --check`; после исправления — также 30 повторов тестов
пакета с `-race` и отдельный регрессионный тест отмены bind. Сборка образа и объединённое
покрытие сообщены исполнителем, но координатором повторно не подтверждались.
Контейнер после рефакторинга не запускался. Итерация 2 согласована пользователем.
Изучение её кода при подготовке этого документа не является полным координационным
ревью или самостоятельным подтверждением успешного запуска её тестов.

Локальный сбор SDK не подтверждает OTLP; тестовый HTTP-получатель не подтверждает
Collector/Prometheus; финальный экспорт не подтверждает последний scrape.
Внешний pipeline, формулы, МИС/Auth, публикация API, `/metrics`, трассировка,
экспорт логов, дашборды и alerting в рамках этого пересмотра не изменяются.
